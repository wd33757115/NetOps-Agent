# NETCONF 接口

维护 NETCONF 接口定义。每条定义把设备的一张 NETCONF 表映射成规则治理检查项的值，产出的行和 CLI 采集的一样（值名相同，写法按 CLI 原文），所以拓扑等使用方不用改归一化代码。

- `backend/mapping.py`：定义的校验、过滤条件生成、XML 转值行。纯数据处理，不连设备。
- `backend/service.py`：定义的草稿、发布和版本；读取设备的 hello 能力；试运行。
- `runtime.py`：给使用方的只读运行时契约（版本 1）。使用方（拓扑）用自己的 NETCONF 会话调用，这里负责选出已发布的定义并映射回包。
- `backend/seeds/`：随 App 发布的种子定义。由 `bootstrap` 以系统版本发布，不会覆盖用户自己发布的版本。

**发布**：按规则治理已发布的检查项核对定义。定义里有检查项之外的值，或缺少必填值时，拒绝发布。

**连接**：
- 只读，走平台的 NETCONF 会话，需要 `device.netconf` 授权。
- 凭据来自平台设备清单的用户名和凭据引用，密码由平台在服务端解析。
- 830 端口第一次见到的主机密钥自动记录，和拓扑发现一致；密钥变化后会话停止，要在 SSH 终端 App 里确认。

**依赖**：device-access（主机密钥存储）、rule-governance（检查项的值）。

**前端**（0.5.0）：沿用防火墙策略 App 的外壳，四步工作流：
1. 接口定义：按厂商、检查项筛选和搜索；新建定义（复制一条相近的定义或从空白骨架开始），新设备型号不改代码。
2. 编辑与发布：定义体按表和值展示（叶子、常量、关联、代码对照、条件），JSON 源码，版本历史，草稿与已发布版的逐行差异；草稿以 JSON 编辑，后端的校验错误原样显示，版本冲突提示刷新；发布时填说明，覆盖检查不通过时列出缺口。
3. 设备能力：设备清单（`GET /devices`）、能力发现、通告的模块和版本、可用与不可用的定义；失败时显示失败码。
4. 试运行：选定义和设备（可用草稿），显示值行、问题清单和耗时；可浏览历史记录。

后端为此只加了 `GET /devices`：清单中启用的设备（名称、地址、厂商、平台、型号，不含登录名和凭据引用）及最近一次能力发现的摘要（通告的模块和版本、同厂商同平台下可用与不可用的已发布定义）。

0.6.0 补齐了 0.5.0 时接口缺的部分：
- `GET /definitions/{id}/versions/{version}`：任一已发布版本的定义体。界面可查看任一版本，比较任意两个版本，并能"以此版本为草稿"；
- 定义列表带模块名，可按模块筛选；
- `GET /check-items/{id}/contract?vendor=&platform=`：检查项在该厂商平台上的值（类型、必填、是否标识），即发布时核对的契约。结构视图列出各值是否已映射；编辑草稿时，随输入实时提示未映射的必填值和检查项之外的值；
- 试运行记录回包（`<data>`，含关联表）的字节数（迁移 `netconf_api_0002`）。
- `POST /devices/{id}/browse`：数据浏览。按命名空间和路径（元素名，从顶层起）读设备的一棵子树，原样返回，并记回包大小和耗时；在"设备能力"里选中设备后使用，可从已有定义带入命名空间和路径，树上任一节点可"设为路径"再读。负责人决定（2026-10-06）：只读，不得改设备配置，其他不加限制。只读由平台保证：过滤条件在后端由元素名生成，平台会话只发带过滤条件的 `get`（运行状态）或 `get-config`（running 配置）。
