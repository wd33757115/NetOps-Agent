# 巡检报告模板设计说明

> 当前按用户要求回到 v1 章节结构，以 `网络设备巡检报告通用模板_v1_表格修订版.docx` 为当前设计底稿。此次仅按用户截图调整 CPU、内存、风扇、电源及接口统计表。v2 数据审核中的取数问题保留作接入参考，不沿用 v2 的章节重组。

> 最新补充：在用户自行修改的上述文件上追加 F、G 两类 CLI 对照附录，另存为 `网络设备巡检报告通用模板_v1_CLI证据修订版.docx`。AI 的输入边界、预算、提示词和人工采纳流程见 `巡检报告AI起草设计与提示词.md`；这些仍是待接入设计。

设计日期：2026年9月6日。模板：`netops.patrol.standard`，版本 1。

本次交付为可编辑的 Word 模板与接入设计，尚未接入 NetOps 模板导入和报告生成接口。模板中的〔字段〕表示待填内容，不是已完成巡检的结果。设计不改变现有检查项、阈值、命令关联或巡检数据。

## 设计结论

采用一份通用交付模板，按本次巡检范围装配章节。正文说明结论、检查覆盖、关键数值、变化和整改事项；完整接口、ARP、MAC、配置原文与日志放明细附件。标准报告由本地程序根据既有结果生成，不依赖模型。用户可以单独选择 AI 辅助起草少数文字段落。

模板制作与实际报告起草是两项独立能力。AI 可以帮助设计章节、措辞、字段及表格，不意味着每次填充报告都要把巡检数据发送给模型。

## 参考材料及取舍

### 用户提供的两份报告

- 2026 年参考文件采用概述、巡检内容、巡检结果、总结、后续工作五章，适合作为交付正文。保留客户与编制信息、设备范围、检查结果表和配置备份附件说明。
- 2017 年参考报告覆盖资产、硬件、接口、冗余、日志及现场检查，提供了较完整的专业分类。保留分类与问题建议思路，减少人员、时间等短内容各占一章的空白页，不逐型号复制章节。
- 2026 年文件名中的季度、正文中的季度与月份存在不一致。新模板分别填写采集时间、报告周期与报告日期，并校验，不能从上传文件名直接推断。
- 两份文件均存在目录域或页码更新问题。新模板使用真实标题样式与自动页码；目录应在最终填充分页后自动生成，不复制旧目录文本。
- 文中的“全部正常”、固定 CPU/内存阈值、超过一年建议重启，以及把异常加白等表述不能作为默认结论。模板不预先承诺完成备份，不把日志告警直接判断为无业务影响。
- 模板不携带两份参考报告的设备名、IP、序列号、联系人或现场位置。

### 公开的专业资料

以下作为报告组织与交付方式的参考，不是本系统所有检查项的判定标准，也不表示当前服务条款或能力承诺。

1. [H3C FIST 巡检指导书](https://www.h3c.com/cn/d_202303/1818442_30005_0.htm)：采用巡检概况、健康状态及设备模块明细的分层展示。其对象主要是服务器与机箱，本设计仅借鉴概况和明细分层方式，不照搬服务器检查项。
2. [H3C 智能巡检设备维护说明](https://www.h3c.com/cn/d_202412/2329879_30005_0.htm)：任务层明确设备范围、执行时间、巡检规则、执行详情与总结报告。本设计将这些元信息纳入报告范围和证据索引。
3. [Cisco Configurable Assessment Service](https://www.cisco.com/c/dam/en_us/about/doing_business/legal/service_descriptions/docs/Configurable_Assessment_Service.pdf)：2014 年公开服务说明强调发现差距、客户反馈及按优先级组织整改建议。本设计采用“问题—证据—建议—负责人—计划日期—复检依据”的闭环记录，不复制其服务范围。

## 正文组织

| 章节 | 读者要得到的信息 | 默认生成方式 |
| --- | --- | --- |
| 封面 | 客户、项目、周期、编制与复核、版本 | 人工元信息与系统版本 |
| 第一章 巡检概况 | 总体结论、采集时间、覆盖差异、优先处理事项 | 结果填充与固定条件语句 |
| 第二章 巡检范围与检查标准 | 设备清单、实际检查范围、判定依据及版本 | 本次范围与标准快照 |
| 第三章 巡检结果 | 资产、资源环境、接口、冗余、地址与转发表 | 标准化记录与已计算结果 |
| 第四章 变化与异常事项 | 基线可比性、配置与日志变化、异常及历史问题复核 | 冻结变化、事件及风险结果 |
| 第五章 巡检总结与后续计划 | 总结、整改与复检、人工补充、复核意见 | 固定语句加人工记录，可选 AI 措辞 |
| 附录 | 交付清单、配置备份、证据编号、版本 | 附件与结果索引 |

Word 中的重复表格行是版式样例。填充时按实际行数展开并重复表头；不是将所有设备限制为一行。主文保留关键结果，大表进入完整明细附件，正文列出总数、展示范围与附件位置。计划内但缺少数据的项目保留缺口提示；不在计划内的类别可隐藏，不能伪装成已检查。

## 结果表达与统计规则

- 健康评估：正常、异常、无法判断、不适用；同时展示完整、部分、缺失等覆盖信息。部分数据正常不能升级为该设备整体正常。
- 事实记录：记录完成、部分记录、未取得数据，不计入健康项目的正常率。当前 7 个事实记录检查项不得伪装为健康评估。
- 周期比较：发现变化、未发现变化、无法比较。当前 3 个变化检查项在单周期任务中标明无法比较，不能写作无变化。
- 所有统计必须标注粒度：设备数按设备去重；检查数按设备与检查项；传感器与接口记录数另计；问题数不能直接使用事件行数。
- CPU 5 秒、1 分钟、5 分钟等窗口分别展示，不拼成一个利用率。内存容量与使用率不混用。光功率区分收发、接口与通道。没有告警阈值不能以严重阈值替代完整健康判断。
- 接口累计错误数不等于错误率。计数重置、基线缺失、时间跨度不可靠时不能计算速率。管理关闭、业务预期与设备“不支持”由检查标准区分。
- 没有连续监控数据，不能以一次季度采样声明整个季度一直正常。
- 离线数据沿用实际采集时间。上传时间、报告生成时间、文件修改时间不能冒充采集时间；对当前状态的证明资格沿用现有报告约束。
- 问题影响范围仅填写有证据或人工确认的信息。技术恢复、待复核、历史未复核和正式关闭分别记录。

## AI 和数据边界

### 默认模式

生成方式默认为“标准模板生成”。字段填充、数值、表格、统计、结论与固定措辞均由本地后端处理。该路径不调用 LLM、模型兜底、隐式摘要、向量化服务或外部图表服务；报告生成失败时也不自动切换到 AI。系统与存储部署位置仍按用户实际环境配置，不把“不调用 AI”误称为整个系统绝对离线。

### 可选 AI 起草

用户可为本次报告启用“AI 辅助起草”，并选择巡检综述、问题说明、整改建议等段落。程序先生成完整标准报告，再对用户选定的段落提出文字修改，不把 AI 作为报告成立的前提。

管理员可禁用外部模型。对外部模型仅构建明确允许的最小摘要，展示将发送的实际内容、模型服务位置与选定字段，由用户明确确认后发送。摘要本身也可能敏感，不能因经过脱敏就自动视为可外发。原始 CLI、配置全文、拓扑、IP、设备名、序列号、账号及联系人默认不进入请求；本地别名映射不随请求上传。

AI 只改写解释和建议，不改写实测值、标准、严重级别、统计、时间与已验证结论，不决定负责人或处理承诺。返回内容检查事实一致性，保留原文及差异，人工可接受、修改或撤回。自托管模型同样由用户主动选择，明确其数据边界；模板配置不得绕过服务端策略。

### 模板制作

模板辅助生成与报告辅助起草分别授权。制作模板可以使用空结构、占位字段和虚构样例；上传真实历史报告用于抽取结构时，先在本地解析和清理身份信息，再决定是否发送必要片段。上传文件不等于授权发送给外部模型。仅使用本地模板编辑也能完成全部配置。

### 验证要求

关闭 AI 时对模型客户端设置测试哨兵：导入、预览、导出、重试及切换模板均不得触发模型请求。AI 路径采用允许字段测试与请求内容复核，测试日志和外部遥测同样不得夹带原文。内容中出现的指令作为参考资料处理，不改变生成策略。

## 与当前代码的衔接

当前存在两条真实路径，不能把已经有 ReportManifest 理解成离线下载也已统一使用它。

| 当前路径 | 已有入口及数据 | 接入方式 |
| --- | --- | --- |
| 离线巡检下载 | `OfflinePatrolJobService.build_result_export` → `build_leadership_report_data` → `render_leadership_docx` | 复用 assessment、scope、metrics、device_inventory_rows、domains、basic_observation_tables、risks、trend、recommendations、limitations |
| 检查项报告 | `build_check_item_report_view` → `render_check_item_docx`，由报告清单固定结果 | 复用 conclusion、coverage、targets、matrix、check_items、report_projection_snapshot、risks、changes、evidence_index |

建议增加薄的统一展示数据适配层，暂不重写采集和判断引擎。将两条路径已有字段映射到相同报告字段；不能得到的数据明确标为缺失，不能调用 AI 补齐。离线已有结果先生成固定的报告输入快照，登记来源任务、分析尝试、采集周期、规则版本、结果摘要；之后模板重排不重新执行规则。

当前离线基本表格和检查项 Word 正文仍偏重版本、电源、风扇、温度、CPU、内存，并非全部 20 项都有完整正文表格。新模板中的接口、冗余和转发区块需要接入已有标准投影或明确补充字段映射，不能声称已经全部可填。

建议映射如下，右侧是现有真实来源；左侧为拟增加的统一字段。

| 拟增加区块 | 离线来源 | 检查项报告来源 |
| --- | --- | --- |
| conclusion / summary | assessment、metrics、limitations | conclusion、coverage、conclusion_dimensions |
| devices / hardware | device_inventory_rows、标准记录 | targets、标准投影 |
| resources / temperature / components | basic_observation_tables、标准记录 | report_projection_snapshot 与 project_report_tables |
| interfaces / redundancy / forwarding | 标准记录，现有结果不足时标缺口 | 按 check_item_id 选择标准投影 |
| standards | 本次实际规则或标准版本，缺失则注明 | 本次冻结检查项与标准快照 |
| changes / issues | trend、risks、structured_event_evidence、unstructured_comparison | changes、risk_issues 或保留明确粒度的 risks |
| actions | recommendations 加人工确认记录 | remediations 加人工确认记录 |
| evidence / trace | evidence 加分析版本及输入摘要 | evidence_index 与 manifest 版本摘要 |
| manual_checks / signoff | 新的人工记录与复核版本 | 新的人工记录与复核版本 |

复用正文风格和编辑体验，不直接拿公文的段落型内容结构承载复杂巡检表格。报告需要重复行、条件区块、结果快照和证据关联。

## 模板文件约定

Word 中已加入带稳定 tag 的文本内容控件，显示为中文〔字段〕。独立的 `template-bindings.design.json` 列出字段和重复表格标识；这些是待实现的绑定契约，当前服务尚不能直接导入运行。

只有模板白名单字段和内置区块可绑定。模板不携带 Python、JavaScript、SQL、任意表达式或网络访问指令。界面以“巡检时间”“CPU 表”“异常清单”等业务名称选择绑定，不要求普通用户输入 JSON 或编写循环。

必需区域包括时间与来源、总体结论及覆盖限制、计划内数据缺口。自定义模板遗漏这些区域时提示补充，不能通过换模板隐去事实边界。

模板与每份报告分别版本化；报告固定结果版本、模板版本、人工补充版本与最终内容。更换模板生成新的报告修订，不覆盖历史文件。人工修改不回写原始巡检事实，已填写负责人、复核意见等需保持来源。

## 首版实施顺序与验收

1. 用本模板打通默认无 AI 的离线报告：本地结果映射、完整 Word、预览、附件索引。
2. 用五类离线样例验收：单周期、双周期、存在异常、部分缺失、全部未形成有效评估。覆盖长设备名、大量接口、表格跨页、没有基线和阈值缺失。
3. 加入模板导入与版本管理，验证换模板不重跑巡检、不改历史结果。
4. 增加可选 AI 文字起草及最小数据发送确认，再接入在线报告的同一展示契约。

验收重点是事实和版式一致：正常不掩盖缺口，历史不冒充当前，事实记录不计健康率，数据区块完整且不截断；报告的标准生成路径在模型不可用或外部网络断开时仍可工作。
