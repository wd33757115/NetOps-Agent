# 网络巡检与巡检规则生成：体验审查与流程重构建议

- 日期：2026-09-05
- 状态：proposed；审查结果与建议，不代表已经实施
- 使用前提：在线、离线巡检都经常使用，按同等重要的主流程设计
- 当前架构基线：[检查项与命令适配器简化方案](./check-item-command-adapter-simplification-remediation-2026-08-10.md)

## 1. 结论

当前两项功能具备不少扎实的工程能力，但前台仍主要按设备管理、样本导入、解析资产和运行流水线组织。用户为了完成一次巡检或补齐一种设备的检查能力，需要自己理解这些内部对象之间的关系。

建议进行**任务流程和信息架构重构**，同时修正结果展示的语义问题。保留检查项、命令适配器、确定性执行、原始证据、版本冻结及发布控制。没有足够证据支持推翻整个执行引擎或重新设计所有数据库表。

两个应用继续独立：

- **网络巡检**负责选范围、选检查内容、取得可信结果、复核和交付。
- **巡检规则工作台**负责让某种设备支持某个检查项，以及修改检查项的判断标准。可将现有“巡检规则生成”改为这个名称，使生成、验证、发布和维护的职责更准确。

二者通过“覆盖缺口 → 制作任务 → 验证发布 → 返回原巡检重新分析”衔接。普通巡检不应变成现场制作规则。

## 2. 审查方法与边界

本次实际打开本地应用，以已有 admin 会话进行只读检查，包括在线发起弹窗、离线任务列表与已有双周期结果、检查项目录、现有 H3C 光功率命令适配器编辑表单，以及规则样本任务的概览、导入进度和导入结果；同时核对相关前后端代码与当前架构文档。

本地实例在线批次列表为空；离线巡检列表有两个历史分析任务，规则样本列表有三个任务。详细检查了其中一个离线巡检和一个规则样本任务。它们只代表本地已有数据，不能用来推断生产整体故障率或误报率。

未连接真实设备发起采集，未重新生成、审批或发布资产，未改动业务配置，也没有开展耗时或并发基准测试。以下明确区分可复现展示问题、流程判断和待验证的业务问题。

## 3. 应当保留的能力

| 现有能力 | 审查依据 | 保留理由 |
|---|---|---|
| 检查项与命令适配器分离 | 当前架构、检查项目录和适配器表单 | 同一检查标准可以跨厂商复用，不必每条命令重新生成判断规则 |
| 发起前预检、目标预览 | 在线启动表单和服务调用 | 必须让用户知道本次实际覆盖哪些设备，不能为了少点按钮移除范围确认 |
| 执行状态与业务结论分开 | 检查项 assessment、页面结论状态 | 命令执行成功不等于设备健康，数据不足必须保留“无法判断” |
| 历史分析与当前现状证明隔离 | 离线任务用途、current-authority API | 历史文件不能自动成为当前设备状态的证明 |
| 不可变版本、影响预览、审批与审计 | 适配器编辑提示、发布流程 | 修改规则需要可追溯；已有生产版本不能被草稿直接覆盖 |
| 生成阶段、下一步、失败诊断和重试 | 命令单元详情、ParserGenerationStep | 已经存在可复用的流程底座，不需要再造一套平行状态机 |
| 原始 CLI、结构化结果、变化与事件证据 | 已有离线结果和证据入口 | 支持工程师复核，防止只有一段无法验证的 AI 总结 |

## 4. 主要问题与优先级

以下 P1 表示应优先处理的结果语义或关键流程问题，P2 表示明显的操作负担，不是安全漏洞评级。

### P1-1：规则验证结果混入了设备健康结论的展示

**已复现。** 规则样本任务 `offline-2412414ed8ec4a5e8949` 的“导入结果”顶部说明“不形成网络健康结论”，下方仍出现“当前风险 0”、绿色“本次已覆盖范围内未发现当前风险”和“下载巡检报告”。同页还显示 Parser Ready 0/17、缺失模板 16。

后端已经返回用途和 `conclusion_allowed: false`，并使用规则资产验证报告类型；前端共用结果组件按 `risks.length` 决定成功颜色和空态，没有对应区分用途。**这里确认的是展示语义冲突，不是证明后端把验证数据写成了生产健康状态，也没有实际下载文件来断言导出内容有误。**

建议：验证页面只展示样本识别、解析覆盖、结果差异、通过/失败用例和下一步制作动作；按钮叫“下载验证报告”。健康/风险结论组件仅用于允许形成该类结论的任务。零风险、没有可判定数据、验证不适用必须有不同空态。

证据：`OfflinePatrolResultPanel.tsx:336–390,599`；`leadership_report.py:749–765,1576–1595`。

### P1-2：历史分析的时间边界没有贯穿结果页面

**已观察到。** 离线任务概览显示“历史分析”和基线/当前周期；进入结果页后，主标题和摘要使用“当前风险”“发现重大网络风险”，周期信息不在结果顶部持续显示。

“当前”在双周期比较里可以表示较新的那一期，但用户也可能理解为现在。应明确显示“分析截至某采集时间的状态”“与某周期比较”“历史分析”，并在页面、下载入口和报告使用一致的范围描述。当前现状证明的资格校验继续保留。

这属于时间语义表达不足，不据此判断现有历史分析计算错误。

### P1-3：巡检启动入口和本次检查内容不够清晰

**UI 与源码均确认。** 离线页顶部仍有打开在线弹窗的“发起巡检”，离线区另有单周期和双周期入口。在线弹窗可以选设备、分组和工单，但检查内容所依赖的 Profile 配置入口位于设备管理，在巡检 App 中不直接提供。

建议统一“新建巡检”入口：先选在线采集或导入文件，再选择或确认巡检方案。发起前必须能回答：检查哪些设备、哪些项目、与哪次比较、预计哪些项目无法判断。已有设备 Profile 可以作为默认方案来源，不能要求每次重新配置。

范围留空按当前筛选展开的行为应转成明确的目标数量与清单。现有预检门禁应保留；不能把这个问题夸大成已证实的误采集。

证据：`DeviceOperationsWorkspace.tsx:2315–2335,3032,3759–3832`。

### P2-1：巡检入口强调运行设施，结果入口强调元数据

**已观察到。** 在 1280×720 视口中，在线发起弹窗先展示 PostgreSQL、Schema、Redis、Broker、Worker、Beat、MinIO 和 Workflow 等运行就绪信息，任务表单位于下方。离线详情默认概览也优先展示流水线与数据集 ID，结论在后面的“巡检结果”页。

建议：环境正常时压缩成一行“可以发起巡检”；只有阻断时展开原因及处置入口。运行中默认展示进度与需要处理的问题，完成后默认展示结果摘要。元数据和系统诊断放在技术详情中。

### P2-2：任务列表不足以支持“找回和继续我的工作”

**已观察到。** 两个离线任务均名为“双周期离线巡检对比”，主要显示创建时间、设备/文件/命令量、执行完成状态；看不到业务范围、风险摘要、未判定项和报告状态。

建议名称默认包含范围与采集周期，例如“核心交换机 · 9 月 3 日 · 与 9 月 1 日比较”，允许修改。列表同时显示执行状态、结论状态与待办，支持按来源筛选。在线/离线可共用任务列表，仍保留各自来源特征。

### P2-3：样本导入完成，不等于用户的规则制作任务完成

**已观察到。** 样本任务显示进度 100%，并明确提示“导入职责到此结束”，要求转到检查项目录归类，然后继续 Parser、Projection、命令适配器与规则。

这段职责划分在工程上合理，但用户的目标是“让设备支持检查”，并非“把文件入库”。目前有待归类入口、命令单元阶段和下一步按钮，不能说完全没有引导；问题是总任务的进度与入口被分散在多个对象页面里。

建议增加一个贯穿全过程的制作任务视图，复用现有样本任务、命令单元和 Parser Job 作为子对象。导入只是一个阶段，列表“完成”应对应已验证发布，或明确写成“导入完成，待制作”。

### P2-4：日常编辑暴露了过多技术字段，缺少结果优先的校对方式

**已观察到。** H3C 光功率适配器表单同时展示兼容条件、型号/版本正则、优先级、Parser 版本、两个来源记录集、多行字段映射、逐字段高级 JSON、输出质量策略 JSON 和本地回放 JSON。源码中的生成界面也要求查看 A→B Projection 与 Observation。

工程师确实需要这些能力，但日常确认应先看到“原始输出 → 解析表 → 标准检查结果”，发现问题后再展开对应模板、映射、单位和主键。一个字段的异常应该能够定位原文和转换过程，而不是要求先阅读全部 JSON。

建议保留专业编辑器，并提供默认的结果校对视图；兼容范围使用已识别设备预填并显示命中样例；高级表达式仍可编辑，不以 UI 简化替代语义确认。

### P2-5：制作任务与平台迁移管理混在同一层级

**源码确认、导航可见。** 检查项目录存在“回放与切换”页，包含全量回放证明、样本数、回放状态、SHA-256、审计链及部署授权。这属于平台切换治理，与新增一个厂商适配器的日常工作不同。

建议将平台全量迁移、切换证明移入管理员工具；制作任务仍保留自身的样本验证、受影响设备预览和发布审批。不能把二者一起删除。

证据：`CheckItemCatalogWorkspace.tsx:1761–1900`。

### P2-6：覆盖信息偏向资产数量，难以回答业务可用性

**已观察到。** 光功率检查项显示“四个命令适配器、v11”；这并不能说明用户这批设备能否执行光功率检查。离线结果显示 Parser Ready 16/17，但也不能直接转换成“哪些检查项、哪些设备无法判断”。现有系统有专门覆盖入口，因此问题是主流程没有充分利用覆盖结果，而非完全没有覆盖管理。

建议以“目标设备 × 计划检查项”呈现匹配、可执行、可判定和缺口；按厂商/设备族聚合。解析比例留作诊断指标，不能作为业务健康覆盖率。

### 待验证：接口异常是否符合业务重要性

本次查看的历史分析有 22 条当前风险，列表中多条 InterfaceDown 被标为重大。仅凭列表无法判断误报：需要核对接口管理状态、预期启用状态、业务重要性、上期状态及实际规则版本。

后续应用真实样本验证：长期闲置口、人工 shutdown、已知维护、首次观测和真正业务链路中断是否被正确区分。若缺少业务上下文，应显示技术异常及影响待确认；不能自动把 down 解释为重大业务中断，也不能自动忽略真实风险。风险聚合要保留依据，不能仅按名称相似合并。

## 5. 目标流程：网络巡检

```text
新建巡检
  → 选择采集来源：在线设备 / 离线文件
  → 确认范围与检查方案
  → 确认采集时间、对比基线与覆盖缺口
  → 执行或分析
  → 查看结论、异常、无法判断项
  → 复核、报告交付与复检
```

### 在线与离线应共享什么

共享巡检任务、方案摘要、结果状态、证据查看、报告和后续动作。不要为了界面统一，把在线执行批次和离线证据资格强行合并成同一种底层记录。

| 环节 | 在线采集 | 离线文件 |
|---|---|---|
| 数据来源 | 选设备/分组，展开实际目标 | 上传文件或使用已有数据集，识别设备与命令 |
| 检查内容 | 选择方案，预览实际匹配命令 | 选择方案，说明文件能覆盖什么、还缺什么 |
| 时间 | 使用实际采集时间 | 识别文件采集时间，缺失或冲突时请求确认，不直接用上传时间代替 |
| 对比 | 自动推荐兼容基线，允许更换或不比较 | 单周期状态检查或双周期对比，允许复用已有周期 |
| 执行 | 展示完成、失败、跳过设备和可恢复动作 | 展示文件识别、证据确认、分析以及需要人工处理的异常 |
| 结论权限 | 按采集质量与执行规则决定 | 默认历史分析；当前现状证明继续走现有资格与审批路径 |

方案应包含检查项版本、必要参数和基线策略，优先复用现有 Profile。发起时冻结本次范围和资产版本。默认动作是使用已发布方案，不让用户现场选择 Parser 或内部规则资产。

### 完成后的页面

结果顶部固定展示：任务名称、来源、采集时间/对比范围、历史或当前状态资格、分析版本。

首屏回答四个问题：

1. 本次发现什么，需要优先处理什么？
2. 哪些设备和检查项已完成判断？
3. 哪些无法判断，为什么，怎样补齐？
4. 报告是否可预览、可下载或需要复核？

下层按“问题清单 / 设备与检查项 / 对比变化 / 原始证据 / 执行详情”组织。技术诊断按需展开。成功、部分完成、无法判断及不适用分别展示，不能通过风险数量推导成功颜色。

报告预览和下载放在固定位置，页面与导出读取同一份冻结结果。正式交付如有现有发布门禁，继续保留；下载历史分析不会自动升级为当前状态证明。

## 6. 目标流程：巡检规则工作台

### 先区分两个不同的用户目标

| 用户要做什么 | 实际工作 | 发布前重点 |
|---|---|---|
| 让新厂商/型号支持已有检查项 | 新建或修订命令适配器，复用已发布的检查标准 | 命令适用性、解析正确性、字段单位、空输出含义、兼容命中 |
| 改变“什么算异常”或新增检查内容 | 新建或修订检查项与判断规则 | 业务含义、阈值依据、正反例、跨厂商影响与历史回放 |

不要让用户每导入一条新命令都重新生成一套判断标准。

### 连续制作任务

```text
新建制作任务，或从巡检缺口进入
  → 导入/复用样本，识别命令和设备
  → 确认目标检查项及预期结果
  → 自动生成解析与字段转换候选
  → 对照原文校验标准结果，定向修订
  → 用正反例及可用的双周期样本回放
  → 查看兼容范围、影响和版本差异
  → 审批发布，返回原巡检验证
```

不是把所有任务压成一个不可退回的向导。工作台保留固定任务身份、进度、样本和当前编辑状态；每个阶段有一个清晰主动作，允许返回修订。一个包含多条命令的导入任务可以有多个独立子任务，某条失败不阻断其他已正确验证的输出。

默认工作界面建议：左侧命令/检查项队列，中间原文与结果对照，右侧当前问题、修订说明及 AI 辅助；技术编辑器在需要时展开。AI 负责提出候选和根据具体失败定向修复，人工确认业务语义，发布资格仍由现有门禁决定。

系统已有阶段、blockers 和 next_action 数据，应优先扩展复用。需要确认子任务的草稿和阶段恢复能力；不能仅依赖页面参数或浏览器局部状态串联所有步骤。

### 验证和发布

解析得到非空表格不等于规则正确。发布摘要应展示：

- 原始 CLI 与实际解析结果、标准字段结果能否对照；主键、类型、单位、空输出语义是否正确。
- 正常、异常、缺失值、设备不支持、合法空输出等用例的预期与实际结果。
- 双周期数据可用时，新增、持续、恢复、不可比较是否符合预期；无有效基线时不能伪造对比结论。
- 新旧版本差异、匹配设备、优先级歧义和将受影响的检查项。
- 当前操作者可以做什么、还缺什么条件、发布后验证方式和回滚指向。

发布页聚合解释所有门禁，但不因此绕过 Parser、适配器和检查项各自的版本与权限要求。第一阶段可把现有子审批聚合展示；是否合并发布事务需另行验证依赖与故障恢复，不能只合并按钮。

## 7. 两个应用之间的闭环

例：巡检报告显示某批 H3C 设备光功率无法判断。

1. 工程师从缺口点击“补齐此检查能力”，系统带入检查项、设备身份、命令、脱敏样本及失败原因。
2. 系统查找已有制作任务，避免同一命令和同一缺口反复创建；已有适配器时优先定位匹配或解析问题。
3. 工程师完成候选校验和发布，看到“影响哪些设备/检查项”。
4. 返回原巡检，选择用新版本重新分析已冻结的原始证据，形成新分析版本并比较差异。
5. 若缺口来自未采集、采集失败或原文截断，提示补采或补充文件，不能靠重新分析凭空补齐。
6. 原报告、原规则版本和原结论保持可查；历史证据不会因规则更新而自动变成当前状态证据。

## 8. 实施边界与顺序

### 第一阶段：修正语义，打通在线与离线巡检主流程

- 按报告用途、结论资格和覆盖状态修正结果页颜色、空态与下载名称。
- 统一新建入口，接入已有方案选择/确认和清晰的范围预览。
- 在线/离线共用任务摘要，完成后默认打开结果，环境诊断折叠。
- 固定周期信息、结论范围、未知项和报告入口。

这一阶段不应以全面数据库迁移为前提。先用应用层摘要适配现有批次与离线任务 API；只有明确需要跨会话草稿或新的关联关系时再做增量迁移。

### 第二阶段：串联规则制作与巡检缺口

- 首页改为“继续制作、待验证、待审批、已发布”，保留检查项目录和覆盖浏览。
- 建立贯穿样本、命令单元、Parser 和适配器的任务详情；复用现有阶段数据与恢复动作。
- 新增适配器和修改判断标准使用不同入口，结果校对优先，高级编辑可展开。
- 接通缺口携带上下文、去重、发布后返回分析的闭环。

### 第三阶段：按真实使用证据完善规模与协作

- 验证分组、批量同类修订、回归样本、版本影响和复检操作。
- 根据实测请求数量、页面耗时和设备规模优化性能。源码中的多数规则查询已有 enabled 条件，不能因组件大就认定所有数据同时请求。
- 将平台切换、全量迁移证明等管理功能从日常制作流程移出。

不建议先只换皮肤，也不建议同时重写采集引擎、解析引擎和报告引擎。应以一个在线巡检、一个离线双周期分析、一个缺口补齐闭环作为第一批可验收切片。

## 9. 验收方式

“测试通过”与“用户无需帮助就能完成任务”应分别验证。

| 场景 | 必须验证的结果 |
|---|---|
| 在线新建巡检 | 发起前看清范围、方案、预计缺口；失败/跳过设备不消失 |
| 离线单周期与双周期 | 文件时间、设备匹配、方案覆盖清晰；历史/当前语义贯穿页面与报告 |
| 部分失败或无可判定数据 | 不出现误导的全绿结论；可以找到原因和适用恢复动作 |
| 规则样本验证 | 不显示设备健康结论，导出入口与实际报告用途一致 |
| 在线/离线使用等价证据 | 相同检查项与资产版本产生一致的标准结果；来源资格差异明确保留 |
| 新厂商支持已有检查项 | 复用标准，不要求重复设计判断规则，结果可回到 CLI 验证 |
| 修改阈值或主键 | 清楚显示失效的验证结果、受影响设备及新旧版本差异 |
| 生成失败、刷新页面、稍后继续 | 已保存工作可恢复，错误定位到具体阶段，不强制重新上传全部资料 |
| 发布后重新分析 | 生成新的分析版本，原报告不被覆盖；缺采集数据明确要求补采 |
| 权限与回滚 | 普通操作者不能绕过发布门禁，版本与证据保持可追溯 |

与实际使用者分别完成两种巡检和一次规则补齐，记录是否需要口头解释、能否指出未覆盖范围、能否找到证据及继续未完成工作。耗时、点击数和失败恢复成本先测基线再定目标，本次不虚构量化改进幅度。
