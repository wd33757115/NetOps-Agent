# P4：规则治理业务包与公共资产边界

日期：2026-09-19。前置：P1–P3。总体计划见 `netops-architecture-implementation-plan.md`。

> 当前状态：**P4 已完成阶段交付与验收；正常本地已安装，未启用常驻服务。**
> 以下早期批次保留实施历史。最新实现与验收见文末“P4 收尾交付”；第八批 Workflow 适配方案已被固定任务方案替代。

## P4-A 交付与状态

本批完成 P4 的第一部分：真实业务源码和前端迁入规则治理目录，建立巡检只读消费契约，
设备资产与凭据实现进入平台。**P4 整体尚未完成，规则治理尚未安装为独立 App。**

梳理发现，规则样本、设备维护、自动生成与巡检仍共用离线任务和部分页面，
任务的历史 `created_by` 还含用户名，不能直接作为平台 Worker 授权的用户 ID。
因此先保持原入口授权、队列语义及数据库结构，在下一批统一交接；
未仅修改前端权限或将现有 `is_admin` 全部改成真。

## 实际变更

1. Parser、ParserGeneration、RuleControl 及目录治理、评估策略、运行包装配/发布、推广反馈
   的实现迁入 `src/apps/rule_governance/backend`。旧模块保留兼容转发，API 实现也已归包。
2. 规则工作台、规则源任务详情、解析/发布/回归组件，以及 `parserApi`、`ruleAssetSourceApi`、
   `commandAutopilotApi` 实现进入包目录。通用离线 HTTP 操作拆到宿主 `offlineJobApi.ts`；
   共享类型暂留宿主，当前路由和授权行为不变。
3. `runtime.py` 定义版本 1 的只读消费接口，巡检运行包读取和 Parser 冻结读取改用该入口。
   保留原序列化格式和摘要算法；新版本发布不替换历史绑定，废弃版本仍可按冻结 ID 读取。
   此契约不要求规则治理 AppGrant，调用方仍负责自身业务及数据访问授权。
4. 设备仓库、连接就绪投影、身份发现、凭据解析进入 `src/platform/inventory`。
   原路径兼容，生产调用改用平台路径；凭据元信息不包含密码。
5. 静态策略、方言提示和治理目录资源跟随实现。生成模板、可编辑映射继续保存在旧运行数据位置，
   避免迁移后错误计算项目根目录，也避免生成结果改变未来应用包摘要。
6. 兼容模块保持异常和 Celery task 对象身份；共享 check_items 导出改为延迟导入，
   修复新目录先加载时的循环导入。旧 task name 和中心 Beat 注册继续有效。
7. 修复设备删除代码中引用未定义 `attributes` 的既有缺陷；新增 SQLite 事务回归，
   验证删除资产时保存历史快照，重复删除返回空且不重复生成快照。

## P4-B 第二部分：任务身份与内部生成调用

日期：2026-09-19。本批补齐部分持久任务的真实用户 ID，为统一 App 授权准备输入；
**身份记录不是授权凭据，本批尚未接通 Worker 的实时 App 准入。**

1. 自动推进的当前执行者、操作历史和发布授权分别记录 `actor_user_id` / `by_user_id`。
   暂停仅记录操作人，不替换正在执行的提交人；恢复可更新执行者，但不篡改原发布授权者。
   重复启动正在运行的任务不会接管身份。历史调用没有用户 ID 时明确保存空值，不从用户名推断。
2. 解析方案将 `requested_by_user_id` 与任务 ID 一起存入现有 JSON 状态；进度更新保留该身份。
   Parser 重试和派发保存 `execution_identity`，Beat 可以承接已记录的人工重试身份，
   显式人工派发则记录当前操作人。下一轮无身份的旧调用会清空上一轮身份，防止错误沿用。
   自动推进向这些子任务传递持久化的用户 ID；对应两类审计事件也使用真实 ID，显示名另存。
3. 工程修订 API 的同步与异步入口从 `CurrentUser` 提取 ID；Celery 消息传递独立字段，
   修订完成后进入新资产与父资产的修订记录。旧七参数队列消息仍能处理，身份标为未知。
   该异步入口目前仍依赖消息保存排队参数，尚无独立 SQL 请求/排空账本。
4. 增加包内 `generators/runner.py`：固定 9 个允许入口，直接执行包内 Python 脚本，
   保留独立子进程、UTF-8 输入输出、包内声明的超时、结构化失败信息及临时文件清理。
   工程修订、Agent Loop 修订和候选资产提交已改用此入口，不再通过宿主 SkillRunner 发现脚本。
   这是可信业务服务内部调用，不是新增 Agent 工具，也不独立提供用户准入。

## P4-B 工程修订持久任务账本（第五批，2026-09-20）

工程修订的同步和异步 API 现在先保存请求，再领取执行。实现位于
`backend/rule_control/engineering_revision_jobs.py`，继续使用现有治理控制状态表
`ParserControlSetting`，键前缀为 `engineering-revision-job:`；与自动推进一样先落在既有存储，
本批不新增 schema。后续清单/数据库交接必须一并接管这些记录，不能因其位于控制表而遗漏备份或排空。

1. 持久保存提交人的真实用户 ID、业务输入、输入摘要、执行阶段、状态和结果。
   同一用户、同一 Bundle、同一请求标识收敛到一条记录；内容变化返回冲突。
   新任务传给资产持久化器的业务幂等键带用户作用域，避免不同用户复用客户端标识时误取同一结果。
2. `netops.rule_governance.revise` 只接收已落库任务 ID，执行者从账本读取身份和输入。
   PostgreSQL 行锁保证单次领取；租约和阶段检查阻止失去执行权的任务继续进入后续步骤，
   终态回写核对领取凭据。新旧入口使用 1740/1800 秒软/硬限制，继续投递 `netops.ai`。
3. Broker 不可用时保留 queued 请求，每分钟恢复调度重投递同一任务 ID；重复消息不会重复领取。
   running 任务超期、非预期异常或资产写入后的失败标为 `needs_attention`，不自动重新生成。
   该状态继续计入未排空数量。阶段检查不能撤销已经发生的资产写入，也不是子进程中途取消保证。
4. 旧七参数 Celery 消息仍按原 delivery ID 接入账本，保留原业务幂等键；没有用户 ID 的记录保持未知，
   不由显示名推断。普通用户只查自己的任务，管理员沿用现有数据管理范围。
   状态查询不再回退到任意 Redis UUID；已过期或未接管的旧结果不会被伪造为可归属的新记录。
