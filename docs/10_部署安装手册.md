# 部署安装

核对日期：2026-09-06。部署配置以仓库中的 Compose 文件和目标环境验证结果为准。

## Windows

统一使用 [Windows 安装部署](windows-deployment.md)：`scripts/windows/` 和 `deployment/compose.windows.yml`。
以下保留 Linux 完整容器部署流程，Windows 不再使用 prod PowerShell 入口。

## Linux：选择运行角色

| 配置 | 服务与用途 |
| --- | --- |
| `docker-compose.yml` + `core` profile | PostgreSQL、Redis、RabbitMQ、MinIO、迁移任务、Django、React、FastAPI、巡检/控制 Worker 和 Beat |
| 再叠加 `docker-compose.ai.yml` + `ai` profile | 完整 AI 网关和 `netops.ai` Worker；规则生成、公文和其他 AI 任务需要 |
| 最后叠加 `docker-compose.prod.yml` | 用显式覆盖的端口列表把已发布端口绑定到 `127.0.0.1` |
| `observability` profile | 可选 Langfuse；旧 RAG/Qdrant 服务已退出 |

生产配置的 `ports: !override` 防止 Compose 把公网端口与本地端口累加。部署前必须使用当前 Compose 解析完整配置；旧版本不识别该标签时先升级 Compose。FastAPI 不发布宿主机端口，外部 API 经 BFF。

前端镜像使用 Node.js 22 和已提交的 lockfile，执行 `npm ci`；构建参数为 `VITE_API_BASE_URL=/api`。

## 准备配置

首次从 `.env.example` 创建 `.env`，按实际环境设置认证密钥、模型、数据库和对象存储参数。已有配置不应被模板覆盖。

```sh
cp .env.example .env
bash scripts/prod/check_env.sh
```

该预检不能代替外层 TLS、防火墙、服务账号和备份安排。Django、FastAPI、Worker 应使用一致的 JWT、数据库、Broker 和对象存储配置。

## 启动完整应用

在项目根目录执行：

```sh
docker compose --env-file .env -f deployment/docker-compose.yml -f deployment/docker-compose.ai.yml -f deployment/docker-compose.prod.yml --profile core --profile ai config --quiet
docker compose --env-file .env -f deployment/docker-compose.yml -f deployment/docker-compose.ai.yml -f deployment/docker-compose.prod.yml --profile core --profile ai up -d --build
```

`migrate` 是唯一数据库初始化作业，执行 `python -m src.platform.database.bootstrap apply`，统一平台、Django、App 迁移与初始数据；后续服务依赖其成功。详见 [数据库生命周期](database-bootstrap.md)。迁移失败先处理日志和数据库状态，不通过跳过依赖强行启动。已有运行环境更新前先备份数据库和对象存储。

`scripts/prod/start.sh` 使用 `WITH_AI=1` 启用 AI；默认核心配置不会自动叠加 AI。启动不再创建演示账号。首次正式管理员使用 Django `createsuperuser` 或现有账号管理流程。冒烟脚本中的账号参数应替换成专用测试账号。

## 验证

1. `docker compose ... ps` 检查迁移完成及服务健康状态。
2. 检查 BFF `/api/health/` 与 `/api/health/diagnostics/`，确认 PostgreSQL、MinIO、所需 Worker 队列和 Beat。
3. 用目标权限账号登录，检查无对应 App 使用权的账号不能调用其业务；显式授权的用户可使用该 App。
4. 在测试范围中验证完整路径：创建巡检、查看结果及报告；规则制作暂停/继续与发布门禁；公文保存和 Word 下载。真实设备、模型和生产资产验证与代码测试分开记录。
5. 校验最终端口列表。仓库提供 `tests/unit/test_production_compose_ports.py`，直接解析 Compose 合并结果，防止覆盖层重新引入公网监听。

React 默认通过本机 `3000` 访问，BFF 为 `8001`。对外 HTTPS 反向代理示例见 [nginx.production.conf.example](../deployment/nginx.production.conf.example)。若反向代理运行在其他容器，应通过明确配置的 Docker 网络连接，不能假设其他容器能访问宿主机的 loopback 绑定。

## 备份、恢复与回退

PostgreSQL 默认同时保存业务 schema 与 Django 的 `django` schema；MinIO 保存证据和导出对象，必须一并备份。默认方案已不是“SQLite 保存用户”。备份脚本保留显式 SQLite 旧环境的兼容复制功能。

[生产备份脚本](../scripts/prod/)生成 SQL、对象镜像和清单。恢复前核对实际数据库名、账号、bucket 和清单内容，并在隔离环境验证；脚本完成提示不能代替恢复演练。

代码回退应保留数据和历史版本。历史迁移不得随代码清理删除；是否可回退到旧 schema 必须单独判断。`docker compose down -v` 会删除数据卷，不用于普通停机或代码回退。

更多诊断见 [运维与排障](11_运维技术手册%20&%20故障排查.md)，代码与文档检查见 [维护与验证](maintenance.md)。

应用发现不等于启用成功，必须完成[能力包部署校验](capability-packages-guide.md)。
