# 资料检索与引用修复（2026-09-21，Assistant 0.6.0）

## 问题与定位

用户问题：`VPC Endpoint使用场景是什么`。旧回答被统一映射为“引用未通过原文校验，本次未发布诊断结论”。
旧轮次没有保存细分校验原因，无法事后断言每次失败的具体触发点。
用同一问题和当前资料复现时，确实出现了引用只在搜索结果中看到、并未 read 的目录行，
服务端抛出 `Answer cites unread lines`。旧实现等 SDK 完成后才校验，因此 Agent 没机会修正。

当前这份手册只发布了 10 个章节；完整 Word 的本地预览可识别 266 个章节。
已发布内容含目录和概述，未包含专门的 VPC Endpoint 使用场景正文。
这会诱发重复搜索与过度扩展引用。本次未擅自扩大已发布章节范围，也未将整份 Word 送给模型。

## 实现

- 保留 DSH 唯一执行器及原生 glob/grep/read。Agent 自行搜索、读取必要行、补读上下文，
  不增加向量库、固定检索工作流、LangGraph 或第二套执行循环。
- 工具开始时显示真实调用的白名单参数：关键词、文件相对路径、offset/limit、业务查询条件。
  工具结束时显示匹配数、读取行数、截断提示及失败状态。小于一秒显示“不足 1 秒”。
  这是 SDK 工具调用记录，不冒充 shell 命令，也不展示模型内部推理。
- 显式排除凭证、草稿正文和原始工具结果，仅持久化有界、脱敏的操作摘要。
  主聊天和 Assistant App 共用面板，刷新后可从原有 progress JSON 恢复，无新增数据表。
- 通过现有官方 MCP 接入只读 `submit_answer` 草稿检查。返回未读行、格式、范围、缺少引用等
  可操作反馈和已读位置，修正继续发生在同一个 SDK run 内。
- 资料不足使用明确的固定提示，不能通过“资料不足”标签透传无依据的模型结论。
- 每轮仍最多 8 次模型调用、12 次工具、90 秒。接近预算时引导并约束进入引用核对，
  已接受的草稿通过适配层完成 SDK 收尾，不再为最终复述额外请求模型。
  超出预算与模型服务不可用分开显示。
- 最终发布前再次校验资料修订、读取行及业务 App 权限；无法修正时不发布未经校验的回答。

这借鉴的是公开可核对的工具与上下文管理方式，并不假定各产品内部采用相同实现：
[OpenAI Codex 模型指导](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.3-codex)
建议使用专用文件/搜索工具；
[Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
讨论按需加载及文件导航；
[DSH 官方工具目录](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-catalog.md)
提供原生 glob/grep/read 和 MCP 能力。具体引用修复与产品事件适配属于 NetOps 实现。

## 限制

来源校验核对的是实际读取范围及原文一致性，不等同于自动证明每个业务推断成立。
真实完整场景回答仍取决于相关正文是否已发布，以及 Word 提取是否遗漏图片等信息。
旧失败记录保留历史内容，无法凭空补出当时未保存的工具参数；新问题才生成完整操作明细。
P6 的网络专家、新题集与目标服务器持续负载验收仍待完成。
