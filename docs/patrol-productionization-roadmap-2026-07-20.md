## 1. 产品边界

本阶段不再扩张零散功能，目标是把已有链路收敛为可上线、可运维、可证明的巡检产品。

两条业务线继续严格分离：

```text
规则资产线（Parser 控制面）
离线样本 -> Parser / Contract / Policy / Rule 候选 -> 验证 -> 审批 -> active

巡检执行线（设备巡检页）
目标设备 -> active 采集与规则资产 -> Snapshot -> State -> Change -> Event -> 报告
```

巡检执行线不得创建或修改规则资产；规则资产线不得把样本验证结果冒充正式网络巡检结论。

## 2. 当前审计结论

截至 2026-07-20，事实链、规则资产控制面、批次记录和报告基础能力已经存在，但“代码能跑”尚不等于“生产可用”。本轮审计得到以下结论：

| 领域 | 当前状态 | 生产缺口 |
|---|---|---|
| 采集与事实链 | 已具备 Snapshot、Observation、Change、Event 及幂等/恢复机制 | 正式发起前未统一校验依赖服务 |
| 调度 | Worker、Beat、批次持久化分发和 reconcile 已存在 | 普通 health 只证明有 Worker，不证明 `netops.patrol` 队列有人消费 |
| 启动脚本 | `scripts/test/start.ps1` 已启动 Worker 和 Beat；Compose 也包含独立 patrol/control/beat | `verify.ps1` 没有验证 Beat、MinIO、Schema 和巡检专用队列 |
| 规则运行时 | 目标设备预检已返回 Parser 与 runtime asset 缺口 | 缺口没有形成统一的批次质量摘要，容易把“可采集”误解为“可判定健康” |
| Workflow | `patrol-change-event` 已包含采集、状态归一、变化检测和事件构建 | 发起前不验证 Workflow 及必需 Skill 是否真实存在且启用 |
| 交付物 | 原始输出、事件、Markdown/Word/JSON 报告接口已存在 | 报告依赖 MinIO 和 Beat，但发起时不校验这两个依赖 |
| UI | 已有设备预检和批次运行视图 | 发起框暴露 `production/parser_validation`、`workflow/direct` 等内部实现选项；平台阻断只在发起失败后暴露 |
| 容量 | 批次历史已服务端分页，分发按 100 台分块 | 尚无 1000/2000 台容量基准和 SLO 证据 |
| 安全 | BFF、RBAC、凭据引用、审计日志已有基础 | 仍需预生产环境验证密钥、网络暴露、备份恢复和审计留存 |

当前本机运行态实测 PostgreSQL、Redis、RabbitMQ、Celery Worker、Celery Beat、MinIO、Qdrant 和 RAG 均正常；Beat 心跳有效。该结果只说明当前实例在线，不能替代巡检专用准入门禁。

## 3. 下一阶段总目标

建立“先证明可交付，再允许正式巡检”的生产准入机制，并用真实样本和容量测试证明以下能力：

1. 依赖故障时不创建无法完成或无法交付的巡检批次。
2. Parser/规则覆盖不足时仍保留原始证据，但报告明确降级，绝不把“无事件”表述为“网络健康”。
3. 运行中错误能够定位到平台、批次、设备、Workflow 步骤和命令五个层级。
4. 1000 至 2000 台设备场景下，列表、分发、状态更新和报告生成均有量化容量结论。
5. 最终报告能够回答：巡检了什么、哪些设备失败、发现了什么、结论可信度如何、依据和整改优先级是什么。

## 4. 分阶段实施

### Phase 0：生产准入门禁（P0，本轮实施）

新增巡检专用 readiness 契约，至少校验：

- PostgreSQL 连接与 Alembic Schema 版本。
- Redis、Celery Broker。
- 存在订阅 `netops.patrol` 的 Celery Worker。
- Celery Beat 调度链路心跳。
- MinIO Bucket 可访问。
- 指定 Workflow 存在，所有必需 Skill 已注册并启用。
- 报告生成与批次恢复任务已注册。

状态语义：

```text
ready     所有硬依赖通过，可发起
degraded  可发起，但资产覆盖或非关键能力存在告警
blocked   硬依赖失败，不得创建批次
```

API 必须在预览时展示门禁结果，并在真正 launch 时重新检查，防止预览后依赖状态变化。阻断响应使用稳定 failure code 和 HTTP 503，且不得写入批次、执行计划或调度任务。

Parser、Contract、Policy、Rule 缺口属于目标数据质量问题，不等同于采集平台宕机：允许保留原始巡检证据，但必须在预览、运行详情和报告中标记降级及缺口，禁止给出“已判定健康”的结论。

### Phase 1：运行可观测与错误反馈（P0/P1）

- 批次时间线按平台准入、目标解析、计划冻结、批次分发、设备采集、状态归一、变化检测、事件评估、报告交付展示完整阶段。
- 每个阶段记录开始/结束时间、输入数量、输出数量、状态、failure code、可重试性和责任对象。
- 批次级展示聚合进度；设备详情只展示该设备的命令与 Workflow 证据，避免两个层级混用。
- 运行中错误通过 SSE 推送，轮询作为断线降级；失败后提供可执行的“重试失败设备”“查看阻断项”“下载失败清单”。
- 定义僵尸任务 SLO：分发、采集、分析和报告均有 lease、heartbeat、超时与 reconcile 证据。

### Phase 2：真实金样板与报告验收（P1）

- 使用 `lixian` 的 Q2/Q3 多厂商样本完成接口状态与光功率回放。
- 使用预生产真实设备执行小批量在线巡检，验证登录失败、空输出、命令不支持、格式变化和恢复事件。
- 报告必须区分：执行完成、数据完整、规则覆盖、当前异常、变化事件和无法判定。
- Word 报告形成领导摘要、范围与成功率、网络现状、重大风险、数据质量、整改建议和证据附录。
- 抽样事件必须能回溯到设备、命令、Snapshot、Parser、Contract、Policy、Rule 和 Workflow Run。

验收阈值：

- 金样板命令执行证据完整率 100%。
- 已声明 structured 的金样板 Parser ready 率 100%。
- 接口 down/up、光功率低/恢复事件命中率 100%，误报率 0%。
- 任一关键资产缺失时，报告可信度必须降级且给出缺口。

### Phase 3：容量、韧性与发布演练（P1/P2）

- 构造 1000/2000 台设备批次，验证服务端分页、分块分发、数据库索引、前端内存和报告物化。
- 记录 API P50/P95、队列等待、单设备耗时、数据库连接占用、Worker 吞吐、失败重试放大系数和报告生成耗时。
- 演练 Worker hard-kill、Beat 停止、Redis/RabbitMQ 短暂中断、MinIO 不可用、API 重启和重复投递。
- 建立容量上限和背压策略，禁止无限制一次性展开设备、Workflow Run 或报告证据。

目标 SLO（首个生产版本）：

- 批次列表 P95 小于 1 秒。
- 发起预检 P95 小于 5 秒（不包含逐设备 SSH 连接测试）。
- 1000 台批次分发不丢目标、不重复创建逻辑 Run。
- 终态批次 5 分钟内形成报告；失败交付必须有明确状态和可重试入口。

### Phase 4：安全与运维闭环（P1）

- 生产环境禁用默认密钥、演示账号、DEBUG、FastAPI 裸露和热重载。
- PostgreSQL、MinIO 执行备份与恢复演练；明确 RPO/RTO。
- 审计发起、重试、归档、规则审批、报告下载和强制操作。
- 为 readiness、队列积压、失败率、僵尸任务、磁盘水位和报告失败建立监控告警。
- 固定镜像版本、数据库迁移顺序、回滚条件和发布后观察窗口。

## 5. Phase 0 验收标准

- `GET /api/v1/devices/patrol/readiness` 返回稳定、可机读的巡检专用状态。
- 预览响应包含同一 readiness 契约和目标级资产质量摘要。
- 任一硬依赖失败时，launch 返回 503，且数据库中不产生新批次。
- UI 在用户发起前展示每项检查、阻断原因和修复建议；blocked 时禁用发起按钮。
- UI 不再向普通巡检用户暴露验证模式、direct task 和任意 Workflow 名称。
- `scripts/test/verify.ps1` 与生产 smoke test 校验巡检 readiness，而不只校验通用 health。
- 单元测试覆盖 ready、degraded、blocked、队列缺失、Workflow/Skill 缺失和 launch 二次检查。
- 真实浏览器完成一次 readiness 展示与巡检预览验收。

### 6.1 本机历史数据修复记录

真实浏览器验收发现 60 个批次长期显示“处理中”。数据库核验确认这些记录全部满足以下条件：

- 目标设备仅由单元测试固定 ID `device-1`、`device-ready`、`device-blocked` 组成；
- 引用的 `workflow-run-1` 不存在；
- 不包含任何真实设备 Workflow Run。

2026-07-20 已按上述组合条件删除 60 个测试污染批次及其设备明细，保留 6 个具有真实 Workflow Run 的历史批次。清理前先完成候选预览，删除后再次核对批次和设备数量。后续同一组单元测试重复执行未再产生数据库记录。
