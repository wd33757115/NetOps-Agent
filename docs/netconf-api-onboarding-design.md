# NETCONF 管理：新增设备不改代码（设计草案）

2026-10-06。目标（负责人）：添加新设备时，不需要去代码里直接修改。本文是待确认的设计，未实施。

## 1. 现状：哪些情况今天要改代码

| 情况 | 今天要做的事 | 是否改代码 |
|---|---|---|
| 已支持家族的又一台设备（如再加一台 VSR） | 设备清单里添加；在"设备能力"里发现一次 | 不改 |
| 已支持家族的新型号，NETCONF 表结构相同 | 同上 | 不改 |
| 已支持家族的新型号，表结构不同（叶子名、代码值不同） | 定义按"厂商 + 平台"匹配，没有型号维度，只能改已有定义，会影响旧型号 | 改不了（只能共用一条定义） |
| 新家族（如 Comware 5、Huawei VRP） | ① 拓扑识别档案 `collectors/profiles/<家族>.yaml`；② 规则治理为该家族发布检查项实现（`system_check_items.yaml`）；③ NETCONF 定义 | ①② 是仓库里的文件，要发版；③ 现在可以在界面里新建 |
| 只有 NETCONF、没有 CLI 实现的表 | 拓扑只对"已发布 CLI 命令"的表尝试 NETCONF（`collect.py` 中 `command_of`），发布时也要求检查项在该平台有实现（`contract_fields`） | 做不到 |
| 设备通告的是标准模块（ietf-interfaces 等） | 仍要按厂商写一条定义 | 每个厂商一份重复数据 |
| 新的值写法（如另一种 MAC 格式） | `mapping.py` 的 `FORMATS` 是代码 | 改代码 |
| 写定义本身 | 要先知道设备 XML 长什么样：今天靠本地抓包、看样本文件 | 界面里做不到 |

0.5.0 的前端已经解决了"新建/复制定义、试运行、发布"这一段。剩下的缺口集中在三处：**看不到设备数据**（写不出定义）、**定义不能按型号或标准模块匹配**、**新家族依赖仓库里的识别档案和规则实现**。

## 2. 设计

### 2.1 设备数据浏览（写定义的前提）

- 新接口 `POST /devices/{id}/browse`：参数是命名空间、从顶层到某张表的路径、数据源（state/running）。后端用 `mapping` 现有的名称校验和平台的 `check_filter` 生成只含名称的子树过滤条件，经平台只读会话读取；回包按 `MAX_REPLY_BYTES` 截断，并记下回包大小。不接受任意 XML，也就不能借它发别的 RPC。
- 前端在"设备能力"里点一个模块，就能逐层展开：每层显示元素、前几行的样例值和叶子路径。点一行元素设为表路径，点一个叶子把它指给某个值。
- 同一个浏览结果可以存成样本（附设备、时间、大小），试运行和以后的回归都能用它离线对照。

### 2.2 结构化编辑与检查项契约

- 新接口 `GET /check-items/{id}/contract?vendor=&platform=`：netconf-api 后端代为读取规则治理的值契约（名称、类型、是否必填，即现在 `contract_fields` 的结果）。编辑器左边是契约的值，右边是取法；没映射的必填值实时标红，不必等到发布才知道。
- 表单编辑和 JSON 源码并存，二者互相同步；JSON 仍是唯一的存储格式。
- 试运行里的"未映射的代码"一键加入代码对照表：原文自动带入，对应的 CLI 写法由人填写（不猜）。
- 列表接口加上模块名，可以按模块筛选；历史版本返回定义体，可以任意两个版本比较，并能"以此版本为草稿"回滚。
- 试运行记下回包大小。

### 2.3 匹配维度：型号与标准模块

- 定义增加可选的 `models`（型号的正则列表），选择时更具体的优先，规则与规则治理的型号例外一致。这样新型号表结构不同时，新建一条带型号的定义即可，不动旧定义。
- 标准模块的定义改为按模块匹配：`vendor: "*"`、`platforms: ["*"]`，必须写 `module` 和最低 `revision`。设备通告了这个模块就能用，与厂商无关。一份 ietf-interfaces 定义服务所有通告它的设备，符合 §13 第 2 条"设备返回标准模块时只做转换与校验"。
- 选择顺序：型号定义 → 厂商平台定义 → 标准模块定义。同一层出现两条时拒绝发布（沿用现有的冲突检查）。

### 2.4 新家族的接入清单

- "设备能力"页加一个**覆盖矩阵**：行是拓扑要的表（检查项），列是 CLI 实现、NETCONF 定义、最近一次试运行结果。每格写明缺什么，并给出去哪里补：规则治理的检查项实现，或本 App 的定义。新家族接入就是把这张表填满，不用翻代码找入口。
- 识别档案和规则实现目前是仓库文件。要做到新家族完全不改代码，需要把拓扑识别档案也做成可发布的数据（和规则治理的实现一样，带版本和审核）。这不属于 netconf-api，列为后续单独的任务。

### 2.5 不做

- 不做可视化拖拽，不做 XPath 编辑器；路径只能逐层选。
- 格式（如 MAC 写法）仍由代码注册，界面里列出可选项。真遇到新格式再加，少量、经过评审，比让定义里写正则更安全。

## 3. 需要负责人决定

1. **标准模块定义**：是否接受 `vendor: "*"` 按模块匹配（2.3）？这会让一条定义服务多个厂商，问题集中，但也集中修。
2. **只有 NETCONF 的表**：没有 CLI 实现时能否采用 NETCONF？如果可以，"与 CLI 值行一致"的验收就要改成"与浏览样本和人工核对一致"，并去掉 `collect.py` 的 `command_of` 前提和发布时的 `no_contract` 限制（改按检查项本身的值契约核对，不要求平台实现）。
3. **数据浏览的权限**：浏览会读取整张表，是否只给有 `device.netconf` 授权且有本 App 编辑权限的人？
4. **识别档案数据化**（2.4）是否单独立项。
