# 规则样本与 TextFSM 制作顺序修正

2026-09-23。版本 1.3.1 已发布并启用；Gateway、前端、两个 Worker 与 Beat 版本一致，应用准入为 200。

## 业务顺序

导入样本 → 识别命令、分割并本地脱敏 CLI 输出 → 待归类检查项 → 人工确认关联检查项 → 依据检查项语义制作 TextFSM / Projection → 验证与发布。

- 导入完成入口进入待归类页，旧 `tab=production` 链接兼容到归类页。移除导入进度与目录中的直接制作入口。
- 新导入任务在完成前对所有命令输出脱敏，保留原始证据；历史导入不伪标为完成新脱敏阶段。
- 生成接口不再隐式修改关联。ParserSpec 请求从已确认关联取得检查项，不能通过传入其他 ID 改变关联。
- ParserSpec 保存检查项版本与摘要；派发 TextFSM、开始语义分析、接收语义分析结果时复核关联。未关联、文本检查项、版本过期或方案与检查项不一致时阻止生成。
- 前端使用后端返回的关联，不再按命令名称自动猜测目标检查项。文本检查项继续使用文本适配器。
- 复用现有固定任务、脱敏器和目录，不增加 Workflow、数据库表或新执行器。

## 页面加载性能修复（2026-09-23）

样本任务详情页实测首次加载 23.284 秒、目录刷新 10.030 秒。主要耗时来自公共链路：可用应用列表重复执行 9 次完整发现；路径遍历多次读取文件元数据；代理与授权请求反复构建 TLS 信任配置并阻塞事件循环。

修复后，可用应用列表在单次请求内复用一次发现结果；应用摘要仍逐次读取实际文件，但使用 scandir 剪枝排除开发目录并复用目录元数据。HTTPX 客户端复用只读 TLS 信任配置，连接、请求身份与授权决定不缓存；保留证书及主机名验证，支持 SSL_CERT_FILE / SSL_CERT_DIR，配置变化随服务重启生效。

公共平台修复已重启 BFF 和 Gateway，未修改业务包摘要，规则治理仍为 1.3.1；正式部署验证通过。权限/系统管理/设备应用 32 项测试、内核/发布/TLS 23 项测试全部通过，包括授权撤销即时生效。未取消任务、未修改样本或关联关系。

同一任务页面复测首次加载 2.401 秒、目录刷新 0.914 秒；账号接口从 7.277 秒降至 0.144 秒，待归类命令接口从 10.739 秒降至 1.283 秒。刷新计时等待对应响应传输完成与加载指示结束；无接口错误或页面脚本错误。以上为本机本次测量，不是所有环境的延迟承诺。

## 自动制作中断恢复与运行时校验（2026-09-23）

规则治理升级为 1.3.4，修复了启动自动制作时复用旧 cancelled Parser 后立即报“应用已停用”的问题。该提示来自上次发布排空记录，并不代表当前应用停用。人工启动或继续会携带一次恢复意图直到 Parser 步骤，消费后不再自动重试失败任务；已有检查规则草稿、样本和审计历史继续保留。

Parser 重试保留 `parser_spec_check_item`，防止已确认的语义方案丢失检查项版本绑定。后续派发仍会核对当前关联，不允许借重试绕过检查项变更检查。界面说明历史取消原因，并在自动制作状态轮询时同步刷新命令详情和 Parser 状态。

恢复光模块样本后又发现旧 NTC 快速方案仅用 `interface` 作为主键，无法区分同一接口的多个光通道。此前生成路径只执行模板，候选虽然显示生成成功，但运行时正确拒绝了重复主键。1.3.4 当时在自动采用本地 NTC 方案前增加运行时兼容性验证（后续已移除自动 NTC 路径，见下文）；正式生成使用既有 `validate_template_runtime_compatibility`，校验主键、字段与正负样本，不增加新的执行器。业务语义仍由独立复核负责，未放宽发布门槛。

对本次 Cisco `show interface transceiver detail` 任务，通过正式 API 保存了新的 ParserSpec 修订，使用 `interface + channel` 主键；原文无通道号的模块级数据声明 `aggregate` 校验默认值，不改写 CLI 原文，不给真实通道编造编号。初次修订的 22 条光功率记录通过验证后，继续发现原 NTC 模板遗漏模块在位信息；尝试现有语义生成流程时，模型返回了没有显式空模式的 allow_empty 方案，该方案被拒绝，未覆盖已确认方案。

随后提交完整的 ParserSpec 和 TextFSM 修订，经正式人工修订 API 回放原始与脱敏样本，生成候选 `4fbc9080-0745-40c4-bcd8-5ffa67dc436b`。它保留全部 66 个接口、72 条记录：38 个模块不在位，12 个模块在位但 DOM 不支持，22 条真实光功率读数（含多通道）。同时保留部件号、序列号和原有阈值。旧候选按既有机制失效，原检查规则草稿不重建。

用户确认继续严格要求：在位模块缺少光功率应标记数据不完整，不以“不支持”豁免，不补零或默认正常；检查项的必需字段约束未修改。完整解析通过不代表业务数据完整或已发布。候选仍须通过标准数据验证及正常复核/发布门槛。

最终通过正式字段转换 API 保存了可执行的人工修订：显式将 `not present` 映射为 `absent`，按实际通道或模块级 `aggregate` 建立维度，保留必需阈值与模块上下文。修复自动候选把字段绑定写成维度表达式的格式错误后，本地与在线执行均返回 `quality_status=partial`，准确报告 12 条在位模块记录缺少 `rx_power_dbm`。任务停在标准数据验证、状态为 needs_attention；Parser 为 succeeded，应用正常启用。现有样本不满足用户选择的严格完整性标准，因此没有发布新运行规则。

提交过程中还修复了人工候选入口未传执行用户的问题：API 使用真实登录用户 ID，重试与同步执行声明该用户并生成独立执行标识；持久化时仍重新验证应用权限及任务标识。没有沿用历史用户身份，也没有跳过授权。

验证：中断恢复、检查项绑定、NTC 与生成服务相关 140 项后端测试通过；人工候选身份与 API 4 项测试通过；前端 5 项测试及生产构建通过，实际浏览器恢复与正式 API 修订成功。另有 4 项既有测试失败已在修改前代码复现：3 项旧集成测试缺少执行用户或引用已不存在的 `interface.oper_status`；1 项字段语义测试同样引用该旧检查项（最终组合回归中明确排除该项）。这些不是本轮新增失败，详见 baseline 日志。

## 移除自动 NTC 模板复用（2026-09-23）

根据用户决定，删除从 NTC 执行结果推导 ParserSpec 的快捷路径、NTC 候选优先选择，以及 NTC 专用的 Value 别名改写、字段裁剪、平台匹配和升级对比工具；同时移除 ntc-templates 项目依赖。正常生成仍依据已关联检查项和脱敏 CLI 样本，保留当前字段契约、真实样本执行、运行时兼容性及独立复核。

需要使用 NTC 或其他外部模板时，工程师自行选择、调整并通过人工 TextFSM 入口上传。上传不会自动改写外部模板 Value；必须通过当前 ParserSpec 校验与正常审批。已有检查项到标准数据的业务转换不属于 NTC 兼容代码，本次不修改其契约或迁移历史检查项。

历史已发布模板、候选内容和来源审计不删除；新一轮生成不再自动复用旧 NTC 来源候选。人工提交的候选及普通生成候选仍可按原有冻结输入匹配规则复验。

验证：87 项生成、复核、检查项绑定与人工提交测试，另 2 项人工提交 API 测试全部通过；前端生产构建通过。已通过既有生命周期安装 1.3.5，包摘要一致。启用检查曾因失效 Beat PID 文件阻止启动而中断，首次归档操作被自动审批拒绝。用户明确授权后，重新确认旧进程不存在，归档 PID 文件并启动 Beat；Gateway、前端、Worker 和 Beat 启用探针全部通过，1.3.5 已正式启用，应用准入为 200。温度任务已核对并恢复为 collecting，1 条样本保留；光功率任务状态未变。发布材料与当前状态见 `.runtime/retire-ntc/`。
