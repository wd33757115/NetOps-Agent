# Parser 控制面产品化改造目标与实施计划

<!-- document-status: superseded -->
> **历史文档，已被取代。** 本文仅保留审计背景，不再作为当前实现依据。
> 当前 Parser 生成架构见 [Simple Parser Pipeline v2](simple-parser-pipeline-v2-2026-07-22.md)。

## 1. 项目目标

将当前面向研发调试的 Parser 控制台改造成可供生产运维、规则工程和审计人员共同使用的资产治理产品。改造完成后，控制面必须满足以下目标：

1. **数据可信**：任何列表、统计和筛选均基于服务端完整数据，不允许因固定上限产生静默截断。
2. **审计可信**：审批、发布、废弃、删除和回填操作必须绑定登录用户、原因和关联请求，不接受浏览器伪造操作者。
3. **发布安全**：Parser、ObservationContract、ChangePolicy、EventRule 必须通过候选、验证、回放、审批和原子发布链路进入生产。
4. **就绪可解释**：分别展示采集、变化分析和事件评估三阶段就绪状态，并给出精确缺口，不使用浏览器启发式推断生产健康度。
5. **任务导向**：主导航按“待处理、资产目录、生成与验证、审批发布、生产覆盖、审计记录”组织，内部数据模型作为筛选和详情信息存在。
6. **规模可控**：万级资产和任务下仍使用服务端分页、搜索和过滤；运行状态采用轻量增量刷新，避免周期性全量拉取。
7. **操作可控**：高风险生命周期操作统一提供影响范围、阻断项、原因、执行状态和审计结果。
8. **可维护**：按领域拆分页面、查询和生命周期组件；列表状态进入 URL，支持刷新、返回和深链接。

## 2. 分阶段实施

### Phase 1：正确性与治理基线

- 为模板、Parser 任务、回填、规则生成任务、Contract、Policy、EventRule、回放和审计列表增加服务端分页、搜索、稳定排序和真实总数。
- 由 FastAPI 认证上下文生成 actor，客户端不再提交或覆盖审计身份。
- 删除 EventRule 直接激活产品入口，统一进入 Rule Asset Bundle 审批；保留受审计的管理员紧急激活 API。
- 前后端统一 `collection_ready / analysis_ready / event_evaluation_ready` 契约。

### Phase 2：任务型工作区

- 将一级工作区调整为：待处理、资产目录、生成与验证、审批发布、生产覆盖、审计记录。
- 待办统一呈现优先级、影响范围、阻断原因、下一步动作和任务年龄。
- 搜索、状态、页码和每页条数写入 URL。
- 资产兼容性明确展示 vendor、family、model、profile、命令、输出签名和匹配优先级。

### Phase 3：安全操作与表单化

- 建立统一生命周期操作对话框，强制填写原因，展示影响和审计身份。
- 条件、阈值、恢复滞回、字段、数据集和设备选择器使用结构化表单。
- JSON 只保留在管理员高级模式，并在提交前执行 Schema 校验。

### Phase 4：规模化与可观测

- 运行中任务使用小型摘要接口和详情级轮询；后续接入 SSE 推送状态变化。
- 统一加载、失败、空数据、无权限和数据截断状态。
- 桌面端使用密集但可扫描的表格，移动端使用摘要列表、筛选抽屉和溢出操作菜单。

## 3. 质量门禁

- 当前数据库记录数超过单页大小时，API `total` 和翻页结果必须准确。
- 审计记录 actor 必须等于认证用户，伪造的请求 actor 不得生效。
- 普通 UI 不得调用 EventRule 直接激活 API。
- 没有 active EventRule 时，事件评估必须显示未就绪。
- 所有生命周期操作必须有原因、幂等行为和行级执行反馈。
- 后端单元测试、前端组件测试和生产构建全部通过。

## 4. 完成定义

只有当上述四个阶段均有代码和测试证据，并完成当前数据规模下的 API/页面验收后，才视为产品化改造完成。局部页面可用或单个测试通过不构成完成。

## 5. 本轮实施结果

### 5.1 数据正确性与规模边界

- 模板、Parser 任务、历史回填、规则生成任务、ObservationContract、ChangePolicy、EventRule、命令 Profile、设备绑定等列表已改为服务端分页，并返回稳定排序、准确 `total` 和 `page_count`。
- 新增统一工作队列查询，将 Parser 生成、历史回填和规则资产任务按优先级与等待时间统一归并；已拒绝、已废弃等终态任务不再占用生产待办。
- 统计卡区分模板资产总量、Active 数量、Parser 进行中和生产 Parser 待办，不再把不同口径混成“任务总数”。
- 页面查询只在对应工作区启用，运行态使用摘要轮询，避免所有标签页同时全量刷新。

### 5.2 发布治理与审计

- 模板、回填、规则资产、命令 Profile 和设备绑定的生产变更操作者均来自认证会话；浏览器不能覆盖 actor。
- 生命周期操作统一要求填写原因，并展示影响、阻断项和审计说明。
- EventRule 的产品入口不允许直接激活；正常路径统一经过 Rule Asset Bundle 验证、回放、审批和发布。
- 自动调度开关、内置规则应急初始化、强制规则操作和设备绑定启用均写入审计记录。
- 内置规则 Provider/Registry 仍保留给兼容、测试和应急使用，但公开入口受权限和理由约束。

### 5.3 规则资产与运行时就绪

- 运行时健康契约拆分为 `collection_ready`、`analysis_ready`、`event_evaluation_ready`，页面直接使用后端事实，不在浏览器中猜测。
- EventRule DSL、编译器和生成器支持精确 `condition.observation_types`，就绪检查可以定位具体 observation type 的规则缺口。
- ObservationContract、ChangePolicy、EventRule 以资产链和发布包形式展示，审批前可见缺口、回放结果、碰撞和阻断原因。
- 设备范围、有效设备和 EventRule 条件改为结构化表单；JSON 退到高级使用场景。

### 5.4 操作体验

- 控制面按“待处理、资产目录、生成与验证、审批发布、生产覆盖、审计记录”组织，URL 保存工作区、子页、筛选和页码。
- 统一待办展示优先级、状态、影响范围、阻断原因、下一步和等待时长，详情入口回到对应领域流程，不在列表中绕过治理。
- 桌面端使用可扫描表格，查看入口并入任务名称，避免固定操作列挤压核心信息。
- 移动端使用任务摘要列表和独立处理按钮，不展示横向裁切的数据表格。

## 7. 剩余边界与下一阶段

本轮完成的是可受控使用的产品化基线，不等同于容量工程全部完成。以下事项仍需继续推进：

1. 运行态目前使用工作区级摘要轮询。任务并发和操作用户进一步增长后，应增加 SSE 事件流，并保留轮询作为断线降级路径。
2. `ParserControlTab` 已拆出工作队列、生命周期、条件表单和运行时资产等领域组件，但容器仍偏大；后续应继续按工作区拆分查询边界和懒加载 chunk。
3. 应建立可重复的万级模板、十万级任务容量基准，验证索引命中、P95 延迟、数据库连接占用和浏览器内存，而不是仅以功能测试代替容量结论。

在完成容量基准前，控制面可以用于当前规模的生产治理，但不应对外承诺“任意规模下的企业级容量”。

## 8. 规则历史投影专项改造

2026-07-19 完成上一节原 P1 投影表目标：

- 新增 `netops_rule_replay_reports`，每个规则任务保留当前历史回放事实和完整回放 JSON。
- 新增 `netops_rule_approval_audit`，批准、拒绝和废弃事件采用确定性 ID 幂等追加，不会因后续验证报告更新而丢失。
- 新增 `netops_rule_agent_loop_attempts`，生成尝试采用稳定身份幂等追加，保留输入、输出、验证反馈和修订请求的脱敏摘要。
- SQLAlchemy 在规则任务插入和更新后，于同一数据库事务同步投影；源 `validation_report_json` 继续作为完整证据保留。
- `0046_rule_job_projections` 在建表后一次性回填历史 JSON，并为成功状态、动作、操作者、阶段、模型和更新时间建立索引。
- 回放、审批和 Agent Loop API 已改为数据库 JOIN、过滤、稳定排序、`COUNT` 和 `LIMIT/OFFSET`，不再扫描全部规则任务或在 Python 中分页。
- 修复控制面二级导航，历史回放、Agent Loop 尝试和审批审计现在可从对应工作区直接进入，不再依赖 URL 深链。

## 9. 离线证据驱动的规则资产生产

### 9.1 产品边界

规则资产生成入口统一收敛到 `Skills -> Parser 控制面 -> 资产生产`。离线文件在这里是
“规则资产生产证据”，不是巡检任务；设备巡检页保留在线巡检与离线巡检，两者都只消费 active 资产。生成上下文必须同时满足：

- 数据集属于 `OfflinePatrolPeriodRecord`，并绑定离线任务和该周期的权威 `PatrolRun`。
- 上下文只投影 `structured_json`，不读取或传递 `raw_text`。
- 隐私报告的范围必须为 `offline_period_authoritative_runs`，且保留不可变摘要。
- API 不接受浏览器手工提交的 `records` 作为生成证据；旧式、无 `offline_job_id` 的上下文即使持有 `context_id` 也不能启动生成。

历史未结构化数据不是新的规则生成入口。工程师可从控制面选择设备和时间范围发起回填，但必须先执行 dry-run，展示命中范围、Parser 资产和预计写入量；确认后再进入受审计的提交阶段，且不覆盖原始历史事实。

正式巡检遇到 `template_missing/parse_failed` 时，只保存 Snapshot、降级状态和证据引用，不自动创建
Parser 或 LLM 生成任务。候选资产只能由 Parser 控制面的离线样本任务触发；历史未结构化数据只能在
控制面由工程师显式选择回填。

### 9.2 九阶段生产流程

Parser 控制面的离线样本任务详情提供“资产生产”工作区，由服务端根据真实数据投影以下阶段：

1. 离线证据建立。
2. 文件预检与设备确认。
3. 导入与结构化。
4. Parser 缺口闭环。
5. 历史数据回填（可选）。
6. 不可变安全上下文构建。
7. LLM 候选资产生成与验证。
8. 工程师复核与修订。
9. 审批发布与运行时生效。

接口返回总进度、当前阶段、唯一主动作、可选次动作、阻断原因和目标深链接。页面不使用装饰性的流程图代替事实，也不要求用户自行判断下一步。

### 9.3 人机协同和发布门禁

LLM 负责生成 ObservationContract、ChangePolicy 和 EventRule 候选，但没有生产发布权。工程师可以查看精确候选快照并执行：

- 接受候选：必须填写可审计理由，仅记录工程复核结论。
- 请求修订：保留原候选和反馈，不修改已生成版本。
- 工程修订：提交完整候选，系统基于原离线上下文重新执行 Contract 校验、Policy 校验、EventRule 校验、历史回放和碰撞检查，并创建新的候选 Bundle。

工程修订不能原地修改父 Bundle 或 active 资产。新 Bundle 仍需再次工程复核；只有验证通过、历史回放通过、`collision_count == 0` 且工程复核为 `accepted` 时，原子审批接口才允许发布。手工内置规则 Provider/Registry 继续作为应急、兼容和测试接口保留，但不用于替代离线数据发现的新规则。

### 9.4 本轮验收证据

- 后端聚焦回归：`111 passed`，覆盖离线来源门禁、旧上下文反绕过、阶段投影、工程修订重验证、审批门禁和运行时兼容。
- 前端组件测试：`18` 个测试文件、`49 passed`，覆盖资产生产下一步动作、可选历史回填、工程复核、移动端样本任务和发布工作区。
- 前端质量检查：ESLint、UTF-8 源码扫描和 Vite production build 全部通过。

### 9.5 后续容量边界

当前工程修订验证在请求内同步执行，适合现有资产规模。进入多人并发生产后，应将修订验证与历史回放迁移到持久化异步任务，由 Celery 执行并通过 SSE 推送阶段状态；同步接口保留为小样本降级路径。该项属于容量与体验增强，不改变本节已经建立的证据、版本和审批边界。

### 9.6 巡检与资产生产的硬边界

```text
Parser 控制面：离线 CLI -> 候选 Parser/Contract/Policy/Rule -> 验证/审批 -> active
设备巡检页：在线采集或离线巡检文件 -> 只读 active 资产 -> State/Change/Event -> 正式巡检报告
```

- 规则样本 API 为 `/api/v1/parser/asset-source-jobs`；离线巡检 API 为
  `/api/v1/patrol/offline-jobs`。二者通过持久化 `purpose` 隔离，都是正式入口，不是别名关系。
- 资产样本 API 拒绝 `publish_events=true`，双周期数据只用于规则回放和碰撞评估。
- 样本预检与 `patrol-raw-ingestor` 投递到 `netops.ai`；正式设备巡检继续使用 `netops.patrol`。
- 甲方领导巡检报告可由在线巡检或离线巡检任务生成；资产生产侧只输出验证/回放报告，不能冒充网络现状报告。

## 10. 按命令生产规则资产控制面

### 10.1 生产单元与资产边界

规则资产不再以单条 Snapshot 或仅以命令字符串作为生产单元，而使用：

```text
vendor + verified profile/family/model scope + canonical_command
```

同一单元聚合多个周期、设备和输出签名；不同厂家、型号或尚未证明兼容的 Profile 必须分开。只有 Snapshot 已实际引用同一 Parser，或型号与 Parser/Profile 精确匹配时，才能进入同一兼容范围。禁止因为“同名命令”或“只有一个历史 Parser 任务”而跨型号复用资产。

设备覆盖按稳定身份 `Inventory UUID → 管理 IP → 设备名 → 导入设备 ID` 去重。双周期任务同时保留 `device_period_count`，但列表中的“设备数”表示物理设备数，避免把 6 台设备的两个周期误报为 12 台。

### 10.2 十阶段状态机

每个命令资产单元独立展示以下真实阶段：

1. 命令输出切片。
2. 身份识别与归组。
3. Parser 生成。
4. Parser 全样本验证。
5. 结构化数据质量。
6. Observation Contract。
7. Change Policy。
8. Event Rule。
9. 确定性验证、历史回放、碰撞检查与工程复核。
10. 审批发布。

每个阶段保存状态、指标、阻断原因、证据引用和唯一下一步操作。LLM 只生成候选；TextFSM 编译、全样本/holdout/回归验证、Schema 校验、历史回放、碰撞检查、工程师修订与审批共同决定是否可发布。未经批准的候选不能被运行时解析器读取。

### 10.3 生产模式与不适用语义

命令单元显式使用以下模式：

- `full_chain`：Parser、Contract、Policy、EventRule 全链路。
- `observation_only`：只形成稳定状态，不生成变化和事件。
- `change_only`：形成变化，但不自动映射运营事件。
- `raw_hash`：只做经治理的原始哈希比较。
- `ignored`：命令不进入规则资产生产。

模式属于 `command_policy.yaml` 的显式治理契约，不由 LLM 猜测。`structured` 命令可配置为
`full_chain`、`observation_only` 或 `change_only`；`raw_hash_diff` 只能使用 `raw_hash`，
`raw_only/not_applicable` 只能使用 `ignored`。启动时会拒绝相互冲突的配置，避免 UI 展示了模式、
运行链路却无法到达。`observation_only` 会跳过 ChangePolicy 和 EventRule，`change_only` 只跳过
EventRule。

若某一厂家/型号/命令范围的全部输出均被确定性分类为 `not_applicable` 或 `unsupported_command`，该范围直接进入 `ignored`，不创建无意义的 Parser 或事件规则任务。其他型号对同一命令有真实数据时，仍保留独立的 `full_chain` 单元。
