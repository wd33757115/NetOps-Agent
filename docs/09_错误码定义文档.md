# API 错误与业务失败

核对日期：2026-09-06。FastAPI 通用错误定义见 [exceptions.py](../src/core/exceptions.py)，映射见[异常处理器](../src/gateway/exception_handlers.py)。

## FastAPI 通用信封

通过通用异常处理器返回的错误包含：

```json
{
  "success": false,
  "error": {
    "code": "validation_error",
    "message": "参数校验失败",
    "details": {}
  },
  "request_id": "request-identifier"
}
```

响应同时带 `X-Request-Id`。`AppError` 保留显式业务 code，领域异常经映射转换，HTTPException 可携带更具体的 code。普通 HTTP 状态映射不包含所有领域码，完整枚举和映射以源码为准。

| HTTP | 通用 code | 常见处理 |
| --- | --- | --- |
| 400 | `bad_request` | 核对请求与当前业务状态 |
| 401 | `unauthorized` | 检查登录、Token 及刷新结果 |
| 403 | `permission_denied` | 检查角色、能力、所有权和操作范围 |
| 404 | `not_found` | 检查资源存在性与可见范围 |
| 409 | `conflict` | 刷新版本或检查重复操作 |
| 422 | `validation_error` | 读取 details，不能只提示“网络错误” |
| 503 | `service_unavailable` | 检查依赖服务和任务就绪 |
| 504 | `gateway_timeout` | 确认后台状态后再决定是否重试 |

未预期异常返回 `internal_error` 并保留服务端日志；不把堆栈或密钥送给客户端。明确的 Skill、数据库、存储、LLM 等失败也有对应领域码。

## BFF、流式与异步区别

Django BFF 的认证及代理错误、已有业务接口的 detail 字段和流式错误不保证与 FastAPI 通用信封完全相同。前端统一使用 [apiError.ts](../web/react_frontend/src/utils/apiError.ts)解析，不在每页只依赖 `error.message` 一种形状。

SSE 一旦开始传输，后续失败通过流事件体现，不能仅看最初 HTTP 200。Celery 入队成功只代表接受任务，业务完成与失败需要读取任务/Workflow 状态。审批、验证或发布冲突不能靠无条件重复提交解决。

排查应同时保留 HTTP 状态、code、request_id 与具体任务 ID。普通用户看到可处理的说明；开发者凭关联标识查日志和服务端证据。权限含义见[权限指南](permissions-guide.md)。
