# 独立 SSH 能力、网络拓扑与数字孪生实施方案

更新：2026-09-28。本文是本次开发的新方案，替代此前粘贴方案中的冲突内容。第 9 节区分本次已实现的首版与后续数字孪生演进，不把方案目标当作已经完成的功能。

## 1. 已确认的边界

1. **原巡检永久保持独立，不修改、不迁移、不替换其 Netmiko 实现。** 原巡检的采集、身份识别、连接测试、备份、输出格式和调用链均不在本项目改造范围内。没有“以后再迁移巡检”的阶段。
2. 新建 `src/platform/device_access/`，独立实现 SSH 设备访问。新模块不导入巡检、DSH 或任何业务 App 的代码。
3. 网络拓扑是独立 App。DSH、拓扑 App、公共人工终端都是新能力的调用方；停用其中任意一项，不应使其他调用方失去基础 SSH 能力。
4. 拓扑登录用户名和密码由用户在拓扑 App 内人工提供。默认只用于本次发现的明确授权范围，不自动读取或覆盖资产库账号。
5. 节点认证失败、无法连接、连接超时或主机信任失败后，等待人工处理。拓扑不自动重试、不轮换密码、不猜测账号。修改密码不能绕过主机密钥校验。
6. **DSH 后续要支持主动 SSH 诊断取证，用于网络故障根因分析，不能仅限于查询已有拓扑。** 由后端受控工具调用公共能力，模型不获得密码和底层会话。
7. 按最新“制定实施方案并实施”的指令，本次推进六阶段首版：公共模块、独立拓扑 App、递归任务与快照、拓扑界面、公共人工终端、DSH 主动诊断。实际支持范围和实验室验收边界见第 9、10 节。
8. **网络拓扑 App 的最终目标是网络数字孪生。** 第一版 LLDP 发现提供可追溯的拓扑基础，后续建设多层网络与服务映射、持续状态同步、历史回放和行为推演。内部模型从首次建库起对齐 IETF 拓扑模型，不能只在导出时转换名称。
9. 用户已确认拼写为 **8345bis**。建模以 RFC 8345 为基础，跟踪 8345bis 相关修订方向及其衍生、扩展模型；正式标准名称、文档状态与本次核实的修订路线见第 6.1 节。
10. **从种子经 LLDP 逐跳扩散，不预设整个网络的厂商、型号或系统平台。** 型号不是创建发现任务的必填信息。每个新目标独立识别，不能继承父节点的命令适配；本条覆盖初版任务级 `profile_id` 影响全部节点的错误实现。

## 2. DSH 生态 SSH 适用性评估

已检查仓库的 `src/platform/agent_runtime/dsh.py`、`dsh_worker.py` 及 DSH 官方文档。当前项目挂载的是文件工具和受控 MCP，并未接入 SSH provider。

DSH 官方 `@deepseek-ai/dsh-ssh` 提供远端文件、进程和沙箱运行环境：要求本地和远端均为 Linux/macOS，配置 OpenSSH alias，并在远端预装 Node/helper；使用 BatchMode，没有交互输入密码流程。这些前提不适合直接登录 Comware、NX-OS 等网络设备，也不覆盖本项目 Windows 运行环境。

因此，本方案选择 **Paramiko + 新编写的网络 CLI 会话层**，不使用巡检 Netmiko 代码。SSH 协议、认证和加密交给成熟的 Paramiko；本项目实现目标授权、提示符读取、超时、输出上限、失败分类和连接生命周期。DSH 通过业务工具调用这一能力。

官方依据（2026-09-27 查阅）：

- [DSH SSH provider 的部署前提与限制](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/ssh/ssh/README.md)
- [DSH SSH 子系统：远端执行环境，不提供专用模型 SSH 工具](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/ssh.md)
- [Paramiko SSHClient：认证、主机密钥、交互 shell](https://docs.paramiko.org/en/stable/api/client.html)
- [Paramiko Channel：输入输出、超时和终端尺寸](https://docs.paramiko.org/en/stable/api/channel.html)

以后若其他 DSH 生态工具支持网络设备，可以验证后新增适配器；替换适配器不改变拓扑任务和诊断接口。不能仅凭名字包含 SSH 就引入。

## 3. 架构与依赖方向

```text
原巡检 ── 原有 Netmiko、原有执行链路（保持原状）

拓扑发现 App ─────┐
DSH 诊断业务工具 ─┼─> platform.device_access ─> Paramiko ─> 网络设备
公共人工终端 ────┘
```

新模块和原巡检可在 Redis 层共享已有全局、站点和设备连接配额键，避免两个入口合计超过设备承载能力。共享配额不是迁移原巡检，也不让新模块依赖巡检 Python 代码。原巡检仍使用原来的实现，新模块有自己的准入实现。

为兼容已有额度，新模块暂时读取现有 `PATROL_*CONCURRENCY*` 配置和 `netops:patrol:ssh:*` Redis 键；不修改原配置含义或旧实现。新入口在 Redis 启用但不可用时拒绝连接。仅关闭 Redis 时使用进程内共享额度，此模式不能保证与原巡检或其他进程合并计数，不应作为多进程生产配额。

## 4. 公共执行契约

应用后端调用 `DeviceAccessService.execute_batch(context, request, on_result=..., should_continue=...)`。

- `context` 由可信后端根据当前用户、App 权限和设备范围签发，包括用户、来源 App、任务以及精确授权项。不能从浏览器或模型参数反序列化为有效授权。
- `request` 仅含目标引用、连接配置引用、后端生成的命令项、超时和预算。不是对浏览器开放的任意命令执行接口。
- 精确检查目标、动作、连接配置及命令白名单；默认无授权。`device.collect` 与后续 `device.terminal` 分离，`device.change` 不开放。
- `Target` 由服务端解析。候选节点的作用域包含管理域、地址、端口；已有关联资产使用统一资产 ID 作为设备配额身份。
- `ConnectionProfile` 由服务端解析。用户名和密码可由 App 的人工输入生成，密码不进入请求、模型上下文或队列消息。现有 `env:` 解析器仅作为服务端可选来源，不是拓扑必须使用的凭据入口。
- `on_result` 在每条命令后调用；调用方保存证据后可返回受权限保护的引用。服务不自建证据数据库。
- `should_continue` 检查任务取消、App 停用、预算和调用方授权；公共层在连接前、命令前后与结果发布前检查租约。
- 同一批命令共用一个 SSH 连接，顺序执行。不同任务与人工终端各自持有连接。

逐命令结果含执行 ID、命令 ID、开始/结束时间、执行状态、完整性、错误码、输出、证据引用和实际驱动版本。SSH 读取完成只表示收到预期提示符；不能推出 LLDP 解析成功、设备没有邻居或设备运行正常。合法空结果由业务采集配置和解析器单独验证。

连接/准入失败和取消以异常携带明确语义；已开始的批次通过回调保留此前已发布的结果。命令失败在逐命令结果中体现。读取超时、断流、分页或输出超过上限时保留已读内容作为不完整证据，关闭会话，不把迟到输出当成下一条命令的结果。

公共驱动不内置厂商业务解析。首版命令集在 `catalog.py`，拓扑解析在自身 `backend/normalize.py`。提示符、编码、分页标记由服务端连接配置控制；关闭分页命令也纳入授权批次。首版有 Comware/NX-OS LLDP 以及诊断接口、路由命令配置，已做合成样本回放；具体设备/软件版本仍须实验室验证。

## 5. 人工凭据与失败处理

### 5.1 创建发现任务

表单包含种子地址、管理域、允许网段、深度与数量预算、采集配置、用户名和密码。用户明确选择凭据适用范围：默认当前选定的种子；可明确授权用于本次任务指定网段内的邻居。

密码仅通过受认证的 HTTPS 提交，服务端生成不透明的临时凭据引用。多 Worker 所需凭据必须采用服务端加密存储与有效期控制；不能只存在 Web 进程内存，也不能把明文放到 Celery 参数、数据库任务参数、日志、审计正文、URL 或浏览器持久化存储。任务结束或取消时撤销当前使用的引用；已被替换的旧引用以及撤销服务暂不可用时的引用，由最多一小时的有效期兜底清理。长期保存作为将来独立的显式选项，不是默认行为。

执行配置冻结凭据版本而非密码。目标领取时核对凭据引用、版本、授权范围和状态。模型和 DSH 工具不能自行选择任意环境变量名称。

### 5.2 节点级人工介入

```text
queued → running → succeeded
                ↘ waiting_for_input
                    ├─ 更新本节点凭据并重试 → queued（新执行令牌）
                    ├─ 确认网络已恢复后重试 → queued（新执行令牌）
                    ├─ 跳过此节点 → skipped
                    └─ 取消任务 → cancelled
```

人工处理项展示目标地址、发现深度、失败类型和证据入口，不显示已提交密码。认证失败提供新的用户名/密码输入；连接失败提供人工确认后重试、跳过或取消。需要变更端口/适配配置时创建新任务。未知/变更主机密钥交由管理员核验，不能用“重试”直接接受未知指纹。

默认凭据更新只影响这个节点。应用到其他节点或本次发现范围必须由用户明确选择，且不能把失败节点的新账号自动写回整个资产库。每次人工操作有幂等请求 ID，核对任务状态、目标版本和权限；重复点击只产生一次有效重试。旧执行令牌、旧凭据版本不能提交新结果。

其他独立可执行节点可以继续采集；所有剩余节点均等待人工时，运行显示 `waiting_for_input`，释放 Worker 与 SSH 配额，不通过长轮询占用连接。没有新凭据或明确重试操作，不重新入队。凭据过期或恢复后无法解密时，同样等待重新输入。

拓扑运行终态是 `completed / partial / cancelled`；节点成功为 `succeeded`，异常为 `waiting_for_input`。存在待人工节点时不得提前宣称完成。用户跳过后发布部分覆盖快照，保留失败与未探索原因，不因失败删除旧拓扑关系。

## 6. 面向网络数字孪生的拓扑 App

本 App 的长期定位是维护与真实网络关联、能够随观测更新并支持分析和推演的数字模型。拓扑发现是入口；拓扑图是其中一个视图。采用标准拓扑模型有利于后续互操作，但仅有 YANG 格式、节点连线或周期性 SSH 采集，并不代表已经完成网络数字孪生。

下面的架构与阶段划分是本项目的设计选择；引用标准和草案作为参考，不宣称这些文档规定了本项目的数据库或实现方式。

### 6.1 标准基线、修订方向与扩展

截至 2026-09-27，本次核实到的参考关系如下。RFC 8345bis 是相关修订工作的称呼；不把它写成一个已经发布、可直接宣称兼容的 RFC 编号。IETF 早期讨论中使用了该称呼，相关建模提案目前可跟踪 SIMAP YANG 草案，该草案替代了早期 RFC 8345 refinements / Digital Map 建模草案。[早期 RFC8345bis 讨论](https://datatracker.ietf.org/meeting/interim-2024-nmop-01/materials/slides-interim-2024-nmop-01-sessa-rfc8345-gaps-for-digital-map-modelling-00)、[SIMAP YANG 文档及替代关系](https://datatracker.ietf.org/doc/draft-havel-nmop-simap-yang/)。

| 参考 | 核实状态 | 本项目用途 |
|---|---|---|
| [RFC 8345](https://datatracker.ietf.org/doc/rfc8345/) | 已发布 RFC | `ietf-network` / `ietf-network-topology` 基础模型；网络、节点、终结点、链路及跨层支撑关系 |
| [RFC 8944](https://datatracker.ietf.org/doc/rfc8944/) | 已发布 RFC | 下一轮二层属性扩展；本次导出只实现 RFC 8345 基线，不宣称已实现该扩展 |
| [RFC 8346](https://datatracker.ietf.org/doc/rfc8346/) | 已发布 RFC | 后续三层单播 IGP 拓扑；不能用它代称所有 BGP、路由表或业务转发模型 |
| [RFC 8795](https://datatracker.ietf.org/doc/rfc8795/) | 已发布 RFC | 后续流量工程拓扑扩展；按实际 TE 用例引入 |
| [RFC 8342](https://datatracker.ietf.org/doc/rfc8342/) | 已发布 RFC | 参考 NMDA 区分预期配置与实际运行状态；本项目场景推演数据另外隔离 |
| [RFC 7951](https://datatracker.ietf.org/doc/rfc7951/) | 已发布 RFC | YANG JSON 编码与命名空间规则 |
| [draft-havel-nmop-simap-yang-03](https://datatracker.ietf.org/doc/draft-havel-nmop-simap-yang/03/) | 活跃的个人 Internet-Draft，尚非正式标准 | 评估双向、多点、跨域、子网、语义与支撑关系等扩展；作为实验性模型配置，不隐式替换 RFC 基线 |
| [draft-ietf-nmop-simap-concept-13](https://datatracker.ietf.org/doc/draft-ietf-nmop-simap-concept/13/) | IETF NMOP 工作组 Internet-Draft，尚未发布为 RFC | 服务与基础设施映射需求、回放和数字孪生用例；原 Digital Map concept 已由 SIMAP concept 替代 |
| [draft-irtf-nmrg-network-digital-twin-arch-13](https://datatracker.ietf.org/doc/draft-irtf-nmrg-network-digital-twin-arch/13/) | IRTF NMRG Internet-Draft，尚未发布为 RFC | 数字孪生的数据、模型、映射、接口与分析逻辑参考；不当作 IETF 标准合规要求 |

采用“稳定 RFC 基线 + 版本化扩展”策略。每个模型配置记录模块名、namespace、revision、特性开关、来源文档/草案版本和摘要；任务、快照、导入导出与推演均绑定确定的模型配置。草案升级先做兼容性和数据转换验证，历史快照仍能按原版本读取。

标准模型与采集/传输协议分层：SSH、后续结构化管理接口或遥测只负责提供观测；规范化后的数据统一进入模型。不能把 SSH 文本格式当作长期数字孪生数据契约，也不要求设备本身原生实现所有拓扑 YANG 模型。

### 6.2 第一版发现与持久化

发现由确定性程序执行，不经过 Agent 循环：种子入队 → 采集 → 解析 → 记录邻居 → 检查范围、授权、主机信任和预算 → 加入下一层目标 → 归并 → 发布快照。

沿用已有平台的 App 注册、Celery、包级迁移、用户与 App 准入，但自建拓扑业务数据。拓扑不成为一种巡检任务，不给巡检 `ExecutionPlan` 新增 topology 动作。

核心实体为 networks、runs、targets、nodes、aliases、termination points、links、observations、snapshots、resolutions。节点与终结点使用网络内复合主键，链路两端受外键约束；保留独立 asset_ref。快照保存模型配置、network_types、supporting_networks，标准导出支持 supporting-node/link/termination-point 字段。首版仅填充 LLDP 观测层，尚无跨层关系采集器。目标去重、人工操作幂等和快照唯一性由数据库约束；任务网络行锁与执行令牌保护并发发布。SSH 等待期间不持有数据库事务。

管理 IP 不是永久设备身份；设备名不能单独触发合并。LLDP chassis/port ID 保留可获取的 subtype，没有返回时记为 unknown。远端端口缺失时停止解析并保存不完整证据，不编造端口。首版按管理域与通告机箱标识聚合候选，不把候选自动认定为已登录资产。多管理地址归并、机箱冲突消解和人工身份确认是下一轮交付项。

图上区分观测新鲜度、邻接验证程度和有证据的运行状态。单侧 LLDP 不标为双侧确认。失败、截断、模板不匹配、预算用尽均不能证明链路消失。

快照包括真实观测窗口、覆盖范围、失败和人工处理状态、未探索原因、采集/模板版本、证据引用及身份归并版本。数据库使用适合事务的关系模型，但字段语义和引用关系必须对齐 RFC 8345；前端布局结构单独投影。标准导出使用锁定的 YANG 模块验证类型、命名空间与引用，草案扩展独立声明。发生不支持的模型转换时明确报错或返回损失清单，不静默丢弃关系，也不把普通 nodes/edges JSON 宣称为标准导出。

### 6.3 从首次建模就保留的能力

以下要求影响第 2、3 阶段的领域模型设计，不要求第一版立即采集所有网络层。

| 维度 | 建模约束 |
|---|---|
| 多层、多域 | 分别建立物理、L2、L3、Overlay、服务等网络视图；第一版仅填充已有证据的层。使用 supporting-network/node/link/termination-point 表达标准允许的支撑关系，额外语义放入独立扩展 |
| 资产与拓扑角色 | 稳定资产实体与网络内 node 分离；同一设备可以在多个网络层出现。节点用 `(network_id, node_id)` 引用，端口包含节点作用域；不能全局按 IP、名称或 node_id 合并 |
| 连接与依赖 | 基线保留 RFC 8345 有向链路。双向展示是投影，多点和跨域连接用验证过的模型配置表示；不能把服务依赖、推断因果或所有关系都伪装成物理链路 |
| 状态与来源 | 采集事实、人工声明、配置/意图、计算推断分别保留来源；冲突保留证据及处理状态，DSH 输出不能无证据覆盖运行事实 |
| 时间 | 同时保存设备观测时间、系统接收时间、有效区间与采集窗口；处理时钟偏差、迟到观测和证据过期。当前视图是可重建投影，历史证据与快照保持可追溯 |
| 运行与场景 | 实际观测、预期状态、假设场景分开管理。场景引用固定基线快照、输入证据和模型版本；模拟结果不得写回实际网络状态 |
| 可重建 | 原始证据 → 版本化解析 → 规范化观测 → 身份归并 → 拓扑/状态投影。模板修订生成新的派生版本，保留原快照含义 |
| 质量与覆盖 | 每种网络层、属性和关系都有覆盖、完整性、新鲜度与支持范围；缺少路由或策略证据时明确不能证明端到端可达性 |

可先采用现有关系数据库和 JSONB 扩展，不以数字孪生为由立即引入图数据库、仿真集群或新微服务。领域契约保持独立，以后根据查询和推演规模再决定存储和执行引擎。

### 6.4 面向数字孪生的公开查询

现有图和快照 API 保留；后续公开查询应能指定网络层、管理域、基线快照/时间、模型配置与实际/场景视图，并返回覆盖和来源。跨层依赖查询、历史回放和场景计算通过拓扑 App 的公开服务提供，不让 DSH 或其他 App 读取私有 ORM。

下列是第一轮拓扑交付所需的业务 API，未来时间查询、场景 API 在对应阶段另行定义：

## 7. 公共人工 SSH 终端

终端底层属于公共能力，票据与业务审计位于独立 `device-access` App，不属于拓扑 App，也不复用 DSH 的 Agent 终端会话。前端使用 xterm.js，拓扑和设备访问页面复用同一个组件；后端通过独立 Paramiko SSH 会话转发输入输出和 resize，不改原巡检。

HTTP 创建短期、单次、绑定用户/设备/连接配置的票据；WebSocket 完成认证、Origin 检查和原子消费票据后才获取配额并连接设备。支持调整尺寸、关闭、空闲超时、最长时限和权限撤销。Redis 保存票据与归属，不保存连接对象。进程退出即会话结束，不自动恢复或重放命令。

人工终端账号权限由设备侧控制，不能依赖字符串过滤保证“只读”。DSH 不接管人工终端。会话审计记录用户、设备、时间和关闭原因；终端录像是单独可选功能。

## 8. DSH 主动诊断与根因分析

DSH 有两类入口，均经过 App 与设备范围授权：

| 类别 | 首版工具 | 执行特征 |
|---|---|---|
| 已有证据查询 | `topology__read_run`、`topology__read_evidence`；`device_access__read_operation`、`device_access__list_connections` | `mutates=False, evidence=True` |
| 主动诊断取证 | `device_access__collect` | `mutates=True`；只在人工选择连接的诊断 workspace 内开放 |

`collect` 仅接收人工创建的短效连接引用、固定诊断配置 ID 和幂等 ID；DSH 场景中的幂等 ID 由服务端生成，不交给模型。不能提交任意 commands、用户名或密码。助手每轮显式选择最多两个连接，专门的 `DiagnosticWorkspace` 至多执行两个不同命令集；同一组合去重，某连接失败后禁止本轮再次登录。普通 `DocumentWorkspace` 仍为只读查询。MCP 主动采集上限 75 秒且受整轮预算约束；普通查询仍为 10 秒。

诊断可以分多轮：DSH 根据已有证据选择下一项已批准采集配置，由后端检查设备范围、调用次数、命令数、时间和全平台连接额度。支持命令包括后续验证过的接口、错误计数、光模块、LLDP、路由邻接、路由表等配置集合；本阶段不预先宣称支持所有厂商。设备输出是数据，不能成为扩展授权或任意执行命令的指令。

缺少凭据或认证/连接失败时，诊断任务也进入人工处理流程；由平台诊断界面收集新的凭据或明确重试。拓扑 App 不是 DSH 凭据收集的唯一入口，停用拓扑不应阻塞独立诊断。

返回 DSH 的证据包含设备、命令配置版本、执行与解析状态、完整性、观测时间、证据引用和覆盖限制。分析应区分“已证实原因”“候选原因”“待验证项”，给出支持及反证；陈旧拓扑、单侧邻居或图上最短路径不能直接证明实际转发路径和唯一根因。凭据失败只表明本轮无法取得证据，不能自动判定业务设备故障。

数字孪生阶段，DSH 还可基于明确的快照和模型版本查询跨层依赖、回放故障时间线、提交隔离场景计算，并按证据缺口请求新一轮授权 SSH 采集。推演交给可测试的计算/仿真模块，DSH 负责选择问题、组合证据和解释结果；模型生成的文字判断不能充当仿真结果。返回结果必须标明“实际观测”或“模拟预测”、基线时间、假设、缺失数据及算法/模型版本。

配置下发、自动修复与 Agent 接管人工终端均不在本方案范围内。

## 11. 首版部署和使用

1. 按平台现有安装流程合并 App 的 `requirements.lock`，执行前端 `npm ci` / `npm run build`。新 App 不新增微服务。
2. 为 Gateway 与拓扑 Worker 配置同一 `DEVICE_ACCESS_CREDENTIAL_KEY`（Fernet 密钥）及现有 Redis；该密钥不得放入代码或浏览器。Redis 中密码加密保存，默认 1 小时过期；Redis 不可用时拒绝创建凭据。
3. 配置 `DEVICE_ACCESS_GRANTS_FILE`，内容按账号 ID、管理域、CIDR 和动作授权。例如下列示例只授权账号 `91` 访问实验网段，不包含密码：

   ```json
   {"91":[{"domain":"lab","cidrs":["10.0.0.0/24"],"actions":["device.collect","device.terminal"]}]}
   ```

4. 配置 `DEVICE_ACCESS_KNOWN_HOSTS` 为服务端经过人工核验的 OpenSSH known_hosts 文件；不同 SSH 端口使用 `[address]:port` 项。不要根据首次连接自动信任密钥。容器部署须显式注入环境变量，并将授权文件与 known_hosts 挂载为只读。
5. 通过现有数据库 bootstrap / App 发布流程部署包级迁移，启用 `topology`、`device-access`，给使用者分配 App 权限。拓扑队列是 `app.topology`，执行器与 30 秒协调任务由包注册机制加载。发布时遵循平台现有停用、迁移、准备、启用流程。
6. 浏览器使用同源 HTTPS/WSS。Django 新增 `/ws/v1/terminals/{session_id}` 转发；本地开发跨端口时，将前端 Origin 加入已有 `CSRF_TRUSTED_ORIGINS`。票据在 WS 首帧传递，不进入 URL，30 秒过期且只能使用一次。终端空闲 120 秒、会话 900 秒、输出 4 MB 封顶；权限每 5 秒复查，浏览器关闭后释放会话。
7. 拓扑 App 新建发现任务时输入本次凭据。新邻居默认要求单独输入；只有勾选“允许用于新邻居”才在任务网段内复用同一短效引用。异常节点选择新凭据/确认重试一次/跳过，或停止整个任务。
   种子平台默认“自动识别”，可选手工指定仅影响种子。LLDP 新邻居始终从自动识别开始；不需要预先填写对端型号。人工处理时可只指定该节点平台而沿用尚有效的本次凭据，也可更新凭据；不自动更改其他节点。
8. 独立设备访问 App 可创建诊断连接、执行一次命令集、打开终端或撤销授权。助手选择这些连接后才开放本轮主动取证；不选择时继续查询既有证据。诊断失败后不会自动再登录，需用户在设备访问界面重新授权或明确发起新操作。

### 已实现的接口

| 范围 | 接口 |
|---|---|
| 拓扑 | `/api/apps/topology/networks`、`/networks/{id}/runs`、`/runs`、`/runs/{id}`、`/imports` |
| 人工处理 | `/runs/{id}/targets/{target_id}/resolve`、`/runs/{id}/cancel` |

RFC 导出是 RFC 7951 编码的 8345 基线，包含本次观测到的链路；新鲜度、候选身份、覆盖、证据和保留的历史关系在原生快照中查看，不能将标准文件独自当作当前健康证明。YANG 文件与校验摘要位于拓扑 App 的 `resources/yang`。没有导出草案扩展或模拟结果。

首版并发边界：新拓扑目标暂未自动关联原资产 ID，因而与原巡检共享全局/默认站点配额，但未关联的同地址目标不能保证共用原巡检的设备级锁。新 SSH 调用方之间使用管理域/地址/端口统一设备锁。后续资产映射仅添加新能力的读取/关联，不改动巡检实现。

解析器依据的字段顺序参考 [H3C LLDP 命令](https://www.h3c.com/en/d_202009/1329183_294551_0.htm) 与 [Cisco NX-OS LLDP CLI](https://developer.cisco.com/docs/cisco-nexus-9000-series-nx-api-cli-reference/latest/lldp-commands/)。自动测试使用合成数据；厂商示例不是全版本支持声明。

## 13. 逐节点自动识别与异构网络扩散（0.2.0）

修正初版的任务级平台假设。发现流程为：种子地址 → 当前节点 SSH 登录 → 有限版本探测 → 确定当前节点命令适配 → LLDP 采集 → 生成未知平台的候选邻居 → 在访问范围、凭据和预算允许时逐个重复。LLDP 的系统描述作为邻居通告证据保留，不直接当作登录目标的平台确认；相邻节点的厂商可以不同。

自动模式在同一个 SSH 会话中最多发送 `display version`、`show version` 两条只读探测命令；识别到支持的平台即停止探测，只执行该平台的分页控制及 LLDP 命令。确定性签名来自 [H3C 版本命令文档](https://www.h3c.com/en/d_202507/2590644_294551_0.htm) 和 [Cisco NX-OS show 命令文档](https://www.cisco.com/c/en/us/td/docs/switches/datacenter/nexus6000/sw/command/reference/vpc/n6k-vpc-cr/n6k-vpc_cmds_show.html)。当前自动适配支持 Comware 与 NX-OS，不把 Cisco IOS、Huawei VRP 或仅有厂商/主机名的文本误判成上述平台；具体硬件型号未知不阻断已确认平台的 LLDP 采集。

所有候选命令都预先经过精确授权，选择器只能跳过，不能添加设备输出或模型提供的命令。每个节点只有一次登录，平台探测与采集共享 90 秒预算；认证、连接、分页、不完整输出或超时不触发重新登录。未知平台或签名冲突不发送厂商 LLDP 命令，保留版本证据并进入人工处理。人工可指定当前节点已有适配、重新自动识别或跳过；完全不支持的平台需要新增验证过的适配，不能靠“重试”宣称兼容。

识别结果、来源（版本探测/人工指定）、证据命令随节点观测保存，前端逐节点展示平台。旧 API 的 `profile_id` 保留兼容，但只作为种子选择；缺省为 `auto`。人工覆盖存于目标 ID 对应的配置，不影响邻居，也不改动历史快照。不新增数据表或迁移，不修改原巡检。

验证记录：公共设备访问、拓扑、终端与 DSH 相关后端测试共 92 项通过，包括 Comware → NX-OS 混合拓扑扩散、人工覆盖不传给邻居、未知平台暂停、超时/分页停止及 loopback 上两个平台的真实 SSH 单次认证。桌面/手机浏览器 8 项流程通过（修正测试中 Ant Design 选择器定位后重跑对应两项）；前端生产构建、Ruff、ESLint 与文档审计通过。实际交换机联调仍待进行，自动识别适配范围仍限于上述两个平台。
