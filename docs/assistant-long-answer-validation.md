# Assistant 0.6.1：完整配置回答截断修复

日期：2026-09-21。

## 问题与证据

用户问题为“M-LAG配置,给出完整的配置文件”。失败轮次已定位并分段读完相关正文，
在 5 次模型请求、6 次工具调用之后记录 `dsh_run_failed`，并没有进入答案引用提交。

用该次资料修订中的 M-LAG 章节（9483 字符、118 行）进行了隔离复现，未发送整份手册：
旧实现最后一次生成输出恰好为 1500 token，模型明确返回 `finish_reason=length`，随后 SDK 未正常完成。
适配层和 SDK 配置中都固定了 1500 token 输出上限。此前只记录 token 合计，丢失了具体结束原因，
历史记录和 SSE 入口又分别退回两条笼统失败提示，使问题看起来像检索失败。

## 修复

- SDK 与模型适配层统一使用 8192 token 单次输出上限；答案核对上限改为 24000 字符。
  这是容量上限，实际消费按输出量计，简短问题不要求生成长答案。
- 从 SSE 中只提取白名单结束原因与数字用量，不保存模型内部推理或原始流。
  在 SDK 消费截断的工具参数前记录 `model_output_truncated`，不发布截断文本或半截配置。
- 历史、执行过程和旧 REST/SSE 入口使用相同的具体失败原因。
- 配置问题覆盖已读原文支持的设备角色；原文仅含示例或缺少现场参数时标为模板，并列出替换项。
- 仍使用唯一 DSH 执行循环、原生文件工具和官方 MCP；没有增加重试执行器、后台队列或固定检索流程。
  原有 90 秒、12 次工具、8 轮模型调用以及按需读取预算保持不变。

## 验证

- 相同片段修复后真实模型运行完成：答案 6866 字符，15 处引用通过；最后一次生成 3145 token，未被截断。
- 43 项相关后端回归通过；Windows 上跳过 1 项 Linux `/proc` 进程树专属测试。
- 新增覆盖：截断普通文本、截断工具 JSON 均不发布；超过旧 12000 字符限制的完整草稿可通过真实 SDK；
  分片 SSE 的结束原因识别；历史/过程/聊天入口错误一致。
- Python Ruff 通过。使用标准启动脚本重新构建并部署 Assistant 0.6.1，保留用户的会话与资料状态。

现场浏览器在原会话重新提交相同问题并完成：5441 字符、8 个代码块、12 处引用均可回查；
4 轮模型请求、5 次工具调用，执行器计时约 21 秒，模型合计输出 2755 token，SDK 正常 completed。
手机无横向溢出，过程面板无严重可访问性问题，浏览器无运行时错误。
全部 6 个启用 App 的部署一致性检查通过，Assistant 0.6.1 已启用。
