# 检查项字段语义编辑

## 一个字段一种用途（2026-10-11，规则治理 1.9.0）

本节取代下文中与之冲突的说明：评估用途不再多选，“全部字段变化事件”开关和手写 `health_policy` 均已退出表单。

每个标准字段只回答一个问题——“这个值怎么用”：

| 用途 | 适用类型 | 表单还需要填 | 巡检时做什么 |
| --- | --- | --- | --- |
| 仅展示 | 全部 | 无 | 只进报告 |
| 阈值参考 | 阈值参考 | 无 | 被其他字段引用为阈值 |
| 变化检测 | 除阈值参考外 | 状态类可填正常/异常状态 | 与上次巡检不同时产生提示事件；状态类填了正常和异常状态后，变坏产生故障事件（重要）、恢复产生恢复事件，一次变化只产生一个事件 |
| 健康判断 | 状态、数值测量 | 状态类：正常和异常状态；数值类：阈值字段，可选趋势提醒 | 状态类：当前值属于异常状态即异常；数值类：超出设备输出的阈值即异常 |

数值健康判断只认设备在同一条记录里输出的阈值字段，不提供固定阈值。上限、下限各可选两个字段，取较严格的一个；不再区分警告与严重两级。设备没有输出阈值时结果为“无法判定”，不当作正常。趋势提醒可选：单位为 percent 的字段可用“利用率上升”，单位为 dbm 的字段可用“光功率下降”；趋势只作提醒，不计入异常。

`health_policy` 是保存时的编译产物（`local_semantics.compile_health_policy`）：阈值来自表单的阈值字段，统计窗口来自字段的固定维度，只有趋势参数取自提交内容；手写的其余内容会被覆盖，用途不是健康判断时整项删除。CPU、内存、光功率原先隐藏的策略在表单中显示为“健康判断”，按表单重新保存得到的策略与原策略相同（见 `tests/unit/test_check_item_value_use.py`）。

字段一经表单保存，就完全由它的用途定义：此前为它手写的事件约束（`event_constraints`）会被丢弃并按用途重新生成，避免要求一批新用途不再产生的事件。数值健康字段由自身的 `health_policy` 直接判定，不再要求当前状态事件规则资产。检查项的评估模式由字段用途推导：有健康判断即“健康与风险”，否则有变化检测即“变化跟踪”，否则“审计证据”；保存时服务端按此覆盖提交值。

每个字段下方直接显示巡检实际执行的判断，例如“高于设备输出的 cpu_high（取较严格的一个）时判定异常”。说明来自 `POST /catalog/check-items/rule-preview`，它用保存和编译检查项的同一组函数处理当前草稿，不写库；表单未填完时返回缺什么。

### 查看正在生效的规则（规则治理 1.9.1）

编辑已发布的检查项时，每个字段下方先写“保存并发布后”的判断；它与现在生效的规则不同时，再列出“现在生效”的内容，相同时只提示一致。两处使用同一组句子（`rule_preview._rule_lines`、`_health_lines`），可以逐句对比。数据来自 `GET /catalog/check-items/{id}/active-rules`：当前版本字段上的阈值策略，加上绑定到当前版本的生效变化策略和事件规则。

绑定在旧版本上、仍为生效状态的规则单独提示：对应当前字段的在该字段下计数，对应已不存在字段的在“巡检时会做什么”下汇总。运行包提供规则时，变化事件只用绑定到该检查项版本的规则（`event_builder.build_events_from_changes`），所以升版后要为新版本补齐规则包和运行包。

脚本发布的目录修订会产生新的版本标识，规则和运行包仍绑在上一版本。`scripts/check_items/publish_runtime_assets.py <检查项 ID>` 按管理员授权自动发布的同一顺序补齐：生成规则包、审批、为每个适配器装配并启用运行包（默认只预览，`--apply` 发布）。规则包审批前需要工程复核，脚本不代签，复核和审批走界面或同名接口。

### 同名契约下没有通道号的记录

同名契约不允许投影改名或补默认值。对象标识里用于细分对象的维度（例如光模块的 `channel`）在原文中没有输出时，这条记录描述的是整个对象，标准化为 `aggregate`（`command_adapter._aggregate_dimensions`），不再整条拒绝。接口、槽位等主标识为空仍然拒绝，同一对象出现两条无通道号记录按主键重复处理。

此前 H3C 单通道光模块的全部记录都因通道号为空被丢弃，光功率从未被判定。另一处原因在检查项本身：`interface.optical_power` 要求每条记录都有 `transceiver_present`，而在位模块不输出任何在位标记。`scripts/check_items/revise_optical_presence.py` 把该字段改为选填并重新绑定已有适配器（默认只预览，`--apply` 发布，`--restore` 还原）。

光功率数据打通后，没插模块的端口会被 `TransceiverAbsent` 规则逐个判为故障。空端口不是故障，只有“原来在位、现在缺失”才是，因此同一脚本给该字段加上 `allow_initial_transition_fault: false`：没有预期状态依据时当前值只记为未判定，两次巡检之间的在位→缺失仍产生事件。这要求设备在模块在位时也输出在位标记；H3C 单通道输出在位时没有标记，上一次巡检就没有“在位”观测，模块被拔出只表现为光功率观测消失，不会触发该事件。2026-10-11 已发布为 v18，并已补齐该版本的规则包（2 条事件规则、1 条变化策略）和 7 个运行包。更干净的做法是在表单里把在位状态设为“变化检测”并填写正常=present、异常=absent，但这需要同时发布新的事件规则并停用旧规则，本次未做。

未经表单保存的既有检查项不受影响：数据库中 92 个活动检查项按新代码编译出的规则与改动前逐字节相同。它们在表单中打开并保存后才按上表执行；带有特殊事件约束的旧字段（例如光模块在位状态）保存前应核对字段下方的说明。

核对日期：2026-09-24。已实施并在本地启用。

## 实施计划

1. 在检查项字段中直接编辑含义、语义类型、评估用途、状态分类；已有观测目录只作预填模板。新增语义不再要求先修改全局 YAML。
2. 数值字段复用现有阈值引用与比较约束，提供字段选择和比较方式编辑，不新增执行器或规则体系。
3. 后端验证当前检查项的局部定义并生成语义快照与摘要；保存仍走检查项草稿、影响预览和发布流程。局部修改不改变其他检查项或已发布规则。
4. 编辑已有检查项优先读取其快照，保留未编辑的高级属性。规则生成、运行装配使用同一快照。
5. 验证新增、编辑、重新打开、非法状态分类、数值字段引用与规则生成；构建前端并按现有能力包流程更新本地服务。

## 数据约定

每个 observations 字段可携带 semantic_definition 局部定义。服务端验证后写入 rule_semantics_snapshot，并以实际内容计算摘要。客户端提供的摘要不作为新草稿的可信依据。

全局 canonical_observations.yaml 继续提供模板；已有检查项不强制迁移，不自动重新发布检查项、规则或运行包。

## 使用方式

在规则治理的检查项目录中新增或编辑检查项。每个标准字段下的“编辑语义与规则用途”支持：

- 输入新观测标识，或从已有目录选择模板；含义说明保存到当前检查项。
- 选择状态、文本、数值测量、累计计数、阈值参考等类型，以及健康判断、变化检测、仅展示等用途。
- 为状态填写允许取值和正常、异常、未知、过渡分类；正常和异常分类用于健康规则生成，分类不得交叉。
- 数值字段可引用同一检查项的上限、下限、严重阈值字段，单位必须一致；缺少阈值时不能通过隐含固定值判定健康。
- 设置精确比较、状态转换、数值变化、计数增量等执行器支持的比较方式。不修改的基线、列表、维度和高级约束保留。

关闭“全部字段变化事件”时仍可逐字段选择变化检测。健康用途还受检查项整体评估模式约束：仅展示模式不执行健康判断。
页面下方“按当前已发布语义预览规则”继续针对已发布版本；草稿修改需先经过影响预览和发布，才用于后续规则制作与运行包装配。

全局模板目录暂不可用时，已有快照和手工新增字段仍可编辑。新增字段必须填写含义说明；修改不会写回全局模板目录。
