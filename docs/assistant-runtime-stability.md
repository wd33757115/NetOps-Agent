# Assistant 0.4.1：引用与运行稳定性

日期：2026-09-21。承接 [0.4.0基础验收](assistant-foundation-validation.md)。
本批针对已发现的延迟和引用失败改进，仍使用DSH唯一执行器、原生文件工具与官方MCP。
巡检等业务App继续固定流程，不增加Workflow、执行器或权限层。

## 改动

1. 每轮问答创建一个授权HTTP连接池，经异步上下文传入工具和监测线程。
   每次请求重新生成凭证并向Django核对授权，不缓存准入决定；不同会话不共用客户端。
   正常退出、异常及初始化时取消均关闭连接。其他业务调用的既有授权行为保持不变。
2. 在每次模型请求中附加服务端本轮已读文件/行范围和业务证据标记，仅有位置，无原文副本。
   不连续已读行分段列出，范围遵守引用行数和长度上限。目录、grep预览和历史回答不会自动成为证据。
   DSH自行决定补读或省略无依据的旁注；最终发布仍严格校验实际已读范围，没有新增自动修复循环。
3. 增加准备、模型流、工具、边界授权检查及最终引用校验耗时，沿用turns.progress JSON存储。
   指标存在包含和并发关系，不能相加当作总耗时；authorization_checks仅统计Bridge边界检查，
   不代表全部内部授权请求。模型HTTP错误和流中断关闭响应，超时归类为provider_timeout。
4. 修复Windows启动/停止脚本按项目路径误停所有Python/Node进程的问题。
   现在仅识别Gateway、Django、Celery和Vite入口；核对PID文件中的进程确为本项目launcher后才停止，
   不再仅凭旧PID操作复用该PID的其他进程。支持npm的`.bin\\..\\vite`实际启动路径。

连接复用参考[HTTPX官方客户端说明](https://www.python-httpx.org/advanced/clients/)；
官方确认[同步Client可跨线程使用](https://www.python-httpx.org/api/)。本实现按运行持有和回收连接，不建立跨进程全局池。

## 性能和工程验证

此微基准不含首次建池时间，只说明重复连接开销减少，不代表整个问答的性能比例。
原始记录：`.runtime/assistant-authority-benchmark.json`。

首轮真实BFF/SSE业务查询：首个过程0.890秒，最终11.688秒，1次MCP工具、1条可回查证据。
该题与上一批52.596秒题目一致，但两次运行时环境负载和提供方响应不受控，不能把全部差异归因为连接复用。

这些分项存在包含关系。最终答案引用校验通过，历史和SSE过程一致，业务原文仍只通过授权引用接口读取。

部署后另外两次相同问题分别11.977秒、11.934秒完成，首个过程0.843秒、0.955秒。

每次均为1次工具查询、1条业务证据；只查询合成的不存在资产名称，没有触发设备采集或改变网络状态。
