# 检查项与规则一起发布

方案确定日期：2026-10-11。第 1 步已实施（规则治理 1.10.0），第 2 步已实施（1.11.0，2026-10-12）；第 3、4 步未实施。

## 要解决的问题

网络工程师定义了检查项之后，不知道变化策略和事件规则何时生成、是否生效；检查项改版之后，旧规则和运行包留在旧版本上，没有界面可以把它们带到新版本。

核对代码后的现状：

- 生成什么由字段用途决定（见 [check-item-semantic-editor.md](check-item-semantic-editor.md)），与样本无关。
- 发布检查项（`CheckItemCatalogGovernanceService.decide`）只切换版本状态，不生成规则。
- 规则只在两处生成：样本命令关联检查项后的自动制作第一步（`command_autopilot_steps.py` 的 `rules` 阶段），或检查项编辑表单底部的“为已发布版本创建规则草稿”。之后还要工程复核、审批、按适配器装配并启用运行包。
- 规则、运行包绑定在检查项版本上。新版本不会继承，也不会自动生成。
- 当前版本被生效运行包引用时，新版本无法发布（影响预览返回 `active_runtime_bundle_requires_check_item_retirement`），界面没有后续路径。
- 巡检规划对没有生效运行包的“检查项版本 × 适配器”返回 `active_runtime_bundle_missing`（`src/core/check_items/planning.py`），匹配到该适配器的设备不执行这项检查。

## 方案

检查项是唯一需要人维护的东西。变化策略、事件规则、运行包是它的编译结果，随检查项版本一起发布、一起切换、一起回退；界面上只读展示，不单独制作、不单独审批。

不变量：生效的检查项版本，它的规则一定已生效；每个生效的适配器都有当前版本的运行包。达不到时在目录上直接标出。

检查项修改后的处理按改动类型区分：

| 改动 | 规则 | 适配器 | 人要做的 |
| --- | --- | --- | --- |
| 名称、说明 | 不变 | 不变 | 确认发布 |
| 字段用途、阈值字段、正常/异常状态 | 重新生成，旧的同时停用 | 不受影响 | 看对照，确认发布 |
| 新增选填字段 | 新字段的规则自动生成 | 仍可用，不输出新字段 | 发布，之后按需更新适配器 |
| 新增必填字段、删除或改名字段 | 重新生成 | 需要更新 | 先用已有样本更新解析，全部通过后一起切换 |

切换之前旧版本继续巡检。

## 分步

1. 看得见（已实施）：目录的“巡检状态”列和检查项详情，只读。
2. 一起发布：新检查项和只改判断方式的修改，发布时规则同步生效；去掉“被运行包引用就无法发布”的死路。发布确认页列出逐字段的“现在生效 → 发布后”。
3. 适配检查与更新：用已有样本检查各适配器是否还适用，不适用的由 AI 更新后再切换。
4. 试算与回退。

已决定（2026-10-12）：审批合并为一次，批准检查项即批准它的规则，不再单独审规则包；适配器跟不上时整体不切换。

尚未核实：现有历史回放能为试算提供什么；规则取消时未恢复的事件如何收尾。

## 第 1 步的实现

`src/apps/rule_governance/backend/check_items/patrol_overview.py`，只读：

- `patrol_status(ids)`：目录每行一个状态，随 `GET /check-items` 当前页返回（`patrol_status` 字段）。92 个检查项首次 0.2 秒，之后一页约 0.05 秒；已发布版本的编译结果按版本缓存。
- `check_item_overview(id)`：`GET /catalog/check-items/{id}/overview`，返回字段、每个字段正在生效的规则句子、各适配器提供哪些字段及是否生效。

状态取第一个没有满足的环节：

| 状态 | 条件 |
| --- | --- |
| 拓扑生成 | 系统基础检查项（`system_items.system_check_item_ids()`，目前是 36 个 `topology.*`）。它们只供拓扑发现使用，不参与巡检，不需要规则和运行包 |
| 未适配设备 | 没有命令适配器 |
| 规则未生效 / 规则待审批 | 当前版本生效的变化策略与事件规则少于定义要求的数量 |
| N 个适配器未生效 | 有适配器没有当前版本的生效运行包 |
| 仅展示 | 没有任何字段参与判断 |
| 生效 | 以上都满足 |

字段用途取自编译结果而不是字段声明的角色：有阈值策略或当前值规则的是“健康判断”，只有变化策略或变化事件的是“变化检测”，被引用为阈值的是“阈值参考”，其余“仅展示”。旧定义里有的字段声明了角色却不产生任何规则，按声明显示会误导。

适配器提供哪些字段取自它的投影定义（`direct_projection_manifest`），是“解析会输出什么”，不是某次巡检的实际数据。

界面在检查项目录：新增“巡检状态”列；点检查项名称打开详情抽屉（`CheckItemOverviewDrawer.tsx`），其中“修改”进入原有编辑表单。

上线时的数据（2026-10-12）：92 个检查项中拓扑生成 36、仅展示 30、生效 2、有适配器未生效 24；没有规则未生效的检查项。这 24 个检查项共有 27 个适配器没有运行包：26 个是没有投影定义的内置适配器（如 H3C fan health、Cisco show ip route raw text），1 个是 Huawei display interface 同名字段。没有适配器停留在旧版本上。

## 第 2 步的实现

`src/apps/rule_governance/backend/check_items/release.py`。批准一个检查项变更（`CheckItemCatalogGovernanceService.decide`）时，在批准自己的事务里依次完成：

1. 新版本生效，旧版本停用（原有逻辑）。
2. 适配器重绑（`_repin_adapters`）：投影适配器的定义里写着它面向的检查项版本，所以每个生效的适配器生成一个指向新版本的新版本，并按新字段重新校验；校验不过就阻止发布。没有投影定义的适配器只补一条关联。
3. 规则生效（`_activate_rules`）：新版本的规则包随本次批准生效，`_approve_bundle` 新增参数 `released_with_check_item`，凭检查项变更免去单独的工程复核，其余门禁不变；旧版本上没有后继的规则一并停用。
4. 运行包切换（`_switch_bundles`）：原来生效的每个适配器，按新版本重新装配运行包并启用，旧运行包随之停用。原来就没生效的适配器不动。

任何一步失败都会抛出 `CheckItemReleaseBlocked`，整个事务回滚，旧版本继续巡检。规则草稿在事务开始前编译（`prepare_rules`），草稿本身不改变任何判断，重试时会复用。

运行包服务、规则审批都通过传入的会话加入同一事务（`_joined`），没有新增一套发布机制。

发布试算（`preview_release`，`POST /catalog/changes/{id}/release-preview`）就是把上面的切换真做一遍再回滚，所以它报告的阻塞和实际发布完全一致。同时给出逐字段的“现在生效 → 发布后”对照，句子来自 `rule_preview`。

影响预览里原来的阻塞项 `active_runtime_bundle_requires_check_item_retirement`（被运行包引用就不能发布）改为提示“运行包会随新版本一起切换”。

规则和运行包只存在于默认数据库。用其他存储打开的目录服务（单元测试的隔离库）没有可切换的资产，保持原有行为和原有阻塞项，由构造参数 `release_derived_assets` 控制。

界面在“检查项变更”详情：新增“发布后巡检会变什么”（`CheckItemReleasePreview.tsx`），只列判断有变化的字段；草稿状态下“发布并切换”一次完成提交和批准，试算不通过时不可点；保留“只提交，由他人批准”。

目前的范围：字段集合不变的修改（改用途、阈值字段、正常/异常状态、说明）和新建检查项。字段增删改名导致适配器不匹配时会被阻止，等第 3 步提供“用已有样本更新适配器”。

验证（2026-10-12，本地环境）：

- 单元测试：适配器重绑到新版本、字段不匹配时阻止切换且原适配器保持生效（`tests/unit/test_check_item_release.py`）。
- 试算：现有草稿“启动配置文件选择 v2”被正确阻止，原因是 5 个适配器不满足同名字段要求；试算前后数据库无变化。
- 真实发布：在页面上用“发布并切换”发布了“接口光功率”v19，相对 v18 只改了英文说明，判断内容不变。结果是 v19 生效，3 条规则、7 个适配器、7 个运行包全部切到 v19，v18 的对应资产同时停用，没有遗留规则。
- 发布后重跑离线巡检任务（原始采集文件）：结论“发现网络异常”，11 项风险、2 项其他变化，报告内容与发布前逐项相同。
- 没有验证的：改变判断的真实发布（例如把某字段改为变化检测）只在试算和单元测试层面覆盖；新建检查项的发布、有规则被取消的发布没有在真实数据上执行。

## 第 3 步（进行中）

已实施（1.12.0，2026-10-12）：

- 字段被删除时，适配器里指向它的映射在发布时自动去掉（`release._fit_projection`），不需要人改适配器；发布试算会列出这些字段。
- 适配器缺少新版本的必填字段时，阻塞原因直接写出字段名和处理办法：先把这些字段设为选填发布，适配器补上后再改为必填。

方向调整（2026-10-12，用户确认）：不再要求“适配器全部更新完再一起切换”，也不走“先选填、补齐后改必填”。新增字段本身不应是破坏性修改：

- 表单新增字段默认选填（1.12.1）。此前默认必填，而必填意味着缺少该值的记录整条丢弃、每个适配器都必须提供，所以加一个字段就会让全部现有适配器不匹配。现有 314 个字段中 258 个本来就是选填。
- 各适配器能提供多少是覆盖度，详情页逐字段、逐适配器可见，不是发布的前提。
- 适配器按需补字段，一次一个。

放弃前两个方案的原因：AI 生成 TextFSM 的流程绑定在已生效的检查项版本上（`parser/check_item_binding.require_parser_check_item`、`command_autopilot._inputs` 在版本不一致时拒绝），无法面向草稿版本生成；多厂商环境里总有设备给不出某个字段，全体就绪不能作为前提。

### 适配器补字段（试验中，未接入界面）

`src/apps/rule_governance/backend/check_items/adapter_fields.py` 的 `trial_add_fields`，只试算，不保存：

- 样本用适配器在巡检中实际解析过的输出（`netops_command_snapshots`，按适配器的各版本取，去重，最多 30 份）。现有 142 个投影适配器的模板都是批量导入的，没有生成时的样本；但每个适配器都有快照。交给模型前用 `sanitize_parser_sample` 脱敏，只给前 3 份。
- 以现有模板为起点调用现有的 `SimpleParserGenerationService`，规格由现有模板的 Value 加上要补的字段推出。
- 基线校验：现有模板不加任何字段时必须先通过校验，否则不交给模型修改。166 个“适配器 × 检查项”组合里 139 个通过，13 个没有快照，12 个模板里没有可区分对象的字段，2 个不通过。
- 只增不改（`extension_only`）：已有 Value 的正则和选项必须逐字不变，已有字段在样本上的解析结果必须不变，否则退回重做。第一次真实试验中模型把已有 Value 的正则改窄了而样本结果相同，所以这一条必须是硬约束。
- 声明不等于提供：新 Value 在任何样本里都没有取到值、而原文里出现了相关字样时，退回一次并附上相关原文行。
- 最终判定用原始输出（不是脱敏副本）逐条回放：已有字段不变，新字段至少在一处取到值才算“提供”；始终取不到的字段从模板里去掉，并报告“这种设备的输出里没有这个值”。

真实试验（Cisco N9K-C9364C `show environment power`，缺 7 个字段，4 份快照）：第一次 1 次模型调用、27 秒，取到 `voltage_volts`（8 条记录都是 12），其余 6 个确认原文里没有，但改动了已有 Value；加上硬约束后第二次没有改动已有 Value，却也没有去捕获 `voltage_volts`，因此又加了“空字段退回一次”。

还没做：保存为新模板并发布适配器新版本（需要像检查项发布那样在一个事务里切换模板、适配器版本和运行包）、界面入口、报告里“该设备未提供”的显示。

## 关系图：字段、规则与事件

工程师问的是三件事：一个检查项关联了哪些变化规则和事件；修改时它们怎么办；删除时它们怎么办。三处用同一张图回答，数据都来自 `src/apps/rule_governance/backend/check_items/relations.py`。

图的语法只有三列：字段 → 判断 → 事件与结果。

- 判断有三种：变化规则（写明比较方式）、健康判断（按设备阈值）、状态判断（按当前值）。
- 事件写明故障、恢复还是提示，以及级别。故障事件显示未恢复数量，提示事件显示已记录数量，点数字列出最近 10 条。
- 健康判断不产生事件，它的结果是“计入当前异常”和“趋势提醒”，画成没有边框的节点。
- 只进报告的字段和只作阈值的字段各收成一行，不占版面。

| 位置 | 内容 | 接口 |
| --- | --- | --- |
| 检查项详情顶部 | 已发布版本的图，带规则是否生效、事件数量 | `GET /catalog/check-items/{id}/overview` 的 `graph` |
| 发布预览（发布后巡检会变什么） | 现版本与候选版本的对比，只画有变化的行，标出新增、变更、停用 | `POST /catalog/changes/{id}/release-preview` 的 `graph` |
| 删除确认框 | 从上到下列出会一起停用的规则、运行包、适配器和会关闭的事件 | `POST /catalog/check-items/{id}/delete-preview` |

两个预览都是“真做一遍再回滚”：发布预览沿用第 2 步的做法，删除预览调用同一个 `retire_check_item` 后回滚，所以预览列出的就是确认后会发生的。

### 事件属于哪个检查项

`netops_network_events` 的 `check_item_id` 列在现有数据里是空的。事件按事件类型归属：某个检查项任一版本的事件规则（生效或已停用）产生过的事件类型，就算它的。一个事件类型只要还有任何检查项的规则在生效，就不会被关闭。

### 修改时

| | 规则 | 事件 |
| --- | --- | --- |
| 规则不变 | 随新版本重新生效 | 不动 |
| 规则被取消 | 发布时停用 | 这类事件发布时关闭 |
| 规则换了条件，事件类型不变 | 新规则生效 | 不动（见下面的限制） |

关闭在 `release_in_session` 的最后一步，和规则、适配器、运行包的切换在同一个事务里；发布被拦下时一起回滚。

### 删除时

以前只要还有适配器或运行包就拒绝删除，能删时规则仍留在“生效”状态。现在 `delete_check_item` 调用 `retirement.retire_check_item`，一次完成：

1. 该检查项全部版本的生效运行包停用。
2. 只为它服务的适配器撤回（连同它们的待发布修改）；还为其他检查项服务的适配器保留。
3. 它的变化规则和事件规则停用。
4. 待发布的修改取消，各版本和检查项本身停用。
5. 它的事件关闭。

系统基础检查项（拓扑生成用）仍然不能删除。保留不动的有：各个版本、历史巡检报告、审计记录、TextFSM 模板。

共用适配器保留后，它的投影定义里仍有被删检查项的那一段输出。运行时按检查项取输出，不受影响；该适配器下次随其他检查项重新绑定时，`_repin_adapters` 会把这段输出去掉。

### 关闭事件的含义

关闭由 `src/core/patrol/change_event_repository.close_events_in_session` 完成：状态改为 `resolved`，并在事件的 payload 里写入 `closed_reason`（`rule_retired` 或 `check_item_deleted`）、`closed_note`、`closed_by` 和 `resolved_at`。不记录恢复、不向外发布，因为并没有观测到恢复。事件记录本身保留；历史报告里各次巡检当时的状态来自发生记录，不受影响。同一类事件以后再出现，会按现有逻辑新开一条。

### 已停用规则留下的事件

2026-10-12 的数据：611 条未关闭事件里，588 条属于 `interface.runtime_statistics` 的 4 个计数器字段（收发字节数、收发包数），它们的变化规则已在早先的版本里取消。这些是“提示”级别的变化事件，本来就不会恢复，只是一直挂着。详情页的关系图下方单列“已停用的规则留下的事件”，并提供“关闭这 N 条事件”按钮（`POST /catalog/check-items/{id}/retired-events/close`，有审计记录）。是否关闭由工程师决定，没有自动清理。

- 真实数据上只做试算，没有删除或关闭任何东西：
  - `interface.optical_power` 的图：`transceiver_present` → 变化规则（状态转换）→ `TransceiverAbsent`、`TransceiverRestored`；`rx_power_dbm`、`tx_power_dbm` → 健康判断 → 计入当前异常、趋势提醒。

  - 删除试算（回滚）：`interface.runtime_statistics` 会停用 38 条规则、5 个运行包、6 个适配器，关闭 610 条事件；`environment.fan` 有 3 个适配器因为还为其他检查项服务而保留。试算前后检查项 92 个、未关闭事件 611 条、生效运行包 187 个，没有变化。
  - 关闭试算（回滚）：`interface.runtime_statistics` 事务内关闭 588 条，回滚后仍是 611 条未关闭。
  - 发布预览：现有草稿 `interface.optical_power` v20 的对比图显示 `transceiver_present` 的判断由“变化规则”变为“状态判断”，新增 `interface_optical_presence_down`，停用 `TransceiverAbsent` 和 `TransceiverRestored`。
- 没有验证的：一次真正带事件关闭的发布、一次真正的删除。两者都会改动现有数据，留给使用者操作。

### 已知限制

- 规则换了条件但事件类型没变时，旧条件下打开的故障事件不会关闭，要等下一次恢复事件。
- 删除检查项时，它还没审批的规则草稿和规则包不处理，留在原状态。
- 被删检查项没有“恢复”入口，需要重新创建。

## 第 4 步：按上次巡检的数据试算

对比图说明规则怎么变，试算说明结果会差多少。位置在发布预览里、对比图下面；数据在 `POST /catalog/changes/{id}/release-preview` 的 `trial` 字段，实现是 `src/apps/rule_governance/backend/check_items/trial.py`。

### 怎么算

巡检把每个采集到的值连同当时检查项版本的语义一起存下来（`netops_state_observations` 的 `metadata_json.semantics`）。试算保留这些值，分别贴上现版本和候选版本的语义，再用巡检自己的当前状态判断函数（`evaluate_current_state`）各算一遍：

- **数据**：这个检查项最近一次巡检的值。“最近”按 `netops_patrol_runs.completed_at`；对比任务里的基线批次（`period_role = baseline`）不算一次巡检，只作为它那次巡检的基线。
- **现在**：现版本的语义，加上当前生效的全部事件规则。
- **发布后**：候选版本的语义，加上其他检查项的生效规则和候选版本编译出的规则。
- **阈值**：一个字段判断时用到的阈值，按候选版本声明的阈值字段，从同一对象的其他值里重新取，因为候选版本可能引用了采集时没有声明的阈值字段。
- 候选版本没有的字段直接略过；候选版本要判断、但上次巡检没有采集到的字段，单列为“无法试算”。

只读：不重新采集，不重新解析设备输出，不写任何数据。

### 显示什么

- 异常：现在几项、发布后几项，多报和少报各几项。一个对象的一个字段算一项。
- 无法判定：缺少阈值或预期状态依据的值的数量。
- 变化来自哪条判断：只列结果有变化的判断，标出新增或停用。
- 多报、少报的逐项清单：对象、设备、字段和值；先列 5 项，可展开，最多 200 项。清单里所有项的字段和值相同、或都在同一台设备上时，会直接写出来。

### 不包括的

- 两次巡检之间的变化事件（例如状态从 present 变为 absent）。这需要重新比较前后两次的值，留给下一版。所以把一个字段从“健康判断”改成“变化检测”后，试算只会显示异常数量的变化，不会显示会产生几条变化事件。
- 适配器的改动：试算不重新解析设备输出。
- 现网巡检的基线：只有离线对比任务能找到对应的基线批次，其余情况下趋势提醒不参与（它本来也不计入异常）。
- “无法判定”是几类原因的数量相加，一个值同时缺阈值和预期状态时会被算两次。

### 验证（2026-10-12）

- `tests/unit/test_check_item_trial.py`（7）、`CheckItemReleaseTrial.test.tsx`（7）。
- 草稿 `interface.optical_power` v20，数据是 10 月 9 日 23:31 那次巡检（1 台设备，253 个值）：异常 11 项变为 51 项，无法判定 44 项变为 0 项；多报的 40 项全部是 `transceiver_present = absent`。11 和 51 与此前完整重跑离线巡检的结果一致，“现在”一列与那次巡检当时的结论一致。
- 草稿 `interface.ip_assignment` v5：候选版本要判断的 `link_status`、`protocol_status` 在上次巡检里没有值，列为无法试算。

### 编辑表单的一处修复（1.13.2）

值类型为布尔的状态字段（如 `transceiver_present`），展开“编辑语义与规则用途”后保存会报 `Cannot read properties of undefined (reading 'map')`：表单显示四个状态分组，没有填的那个在保存时是空值而不是列表。现在没填的分组不参与保存。

## 第 4 步：回退到上一个版本

入口在检查项详情右上角的“回退到 vN”，N 是当前版本之前、上一个真正发布过的版本；被撤销或被拒绝的草稿没有生效过，不算。只发布过一次的检查项没有这个按钮。

### 回退是再发布一次

版本从不重新激活。回退是把上一个版本的内容作为一个新版本起草，再走和普通发布完全相同的路径：

- 规则、适配器、运行包随新版本整体切换，切不过去就什么都不动；
- 新版本不再有的规则留下的事件一并关闭；
- 历史是一条直线：v19 回退到 v18 的内容，得到的是 v20，v19 仍在历史里，对 v20 再回退一次就回到 v19 的内容。

这样做不需要另一套“撤销发布”的逻辑，适配器在两次发布之间改过也不要紧：它们会按回退后的字段重新校验。

### 确认前先看结果

点“回退到 vN”后弹出确认框，内容就是发布预览：对比图（现在与回退后）、会关闭的事件、按上次巡检的数据试算、能否整体切换。确认按钮在不能整体切换时不可用，并写明原因。

发布预览需要一份真实的草稿才能在服务端试切换，所以打开确认框时就起草了（`POST /catalog/check-items/{id}/rollback-preview`，变更原因记为“回退到 vN”）。确认后提交并批准这份草稿，发布的就是刚才看到的内容；不确认就离开，确认框会撤销它（`POST /catalog/changes/{id}/discard`）。浏览器在中途被关掉时草稿会留在“变更与审批”里，可以在那里撤销。

### 名称和说明

检查项的名称、类别和说明存在检查项上，不在版本里；每次通过界面发布时，当时的写法记在那次变更里。上一个版本如果是这样发布的，回退会连同名称和说明一起恢复；如果它是种子数据或脚本导入的，没有这份记录，名称和说明保持现在的内容，确认框里会说明。

### 撤销草稿

“变更与审批”里打开一份还没提交的草稿，操作区多了“撤销草稿”。撤销后变更记为已取消，草稿版本记为停用（它从未生效），已发布的版本不受影响；预览时为它编译的规则草稿一并拒绝。已提交或已审批的变更不能撤销。

### 验证（2026-10-13）

- `tests/unit/test_check_item_rollback.py`（5）：回退起草的是上一个发布过的版本、发布后内容和说明都回去、再回退一次回到刚离开的版本、种子版本不恢复说明、只发布过一次时拒绝、撤销草稿及其边界。
- `CheckItemRollbackDialog.test.tsx`（5）：打开即核对、确认才提交并批准、离开时撤销草稿、不能切换时按钮不可用并说明原因、准备失败时不撤销任何东西。

- 没有验证的：一次真正确认的回退。它会切换现有版本，留给使用者操作。
