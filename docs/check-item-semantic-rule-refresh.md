# 检查项变化策略与事件规则重建

核对日期：2026-09-24。当前规则已发布，思科与华三手工样本对应的运行包已启用。

## 范围与结果

以数据库当前启用的 45 项检查项为准，读取其固定版本、Value、判断模式、状态分组、
阈值引用和事件约束，使用现有检查项规则编译器重新生成。没有调用模型，也没有从
单次 CLI 样本推导告警阈值。TextFSM、Value 命名及“接口状态运行信息和统计信息”定义未改变。

| 检查项 | 新变化策略 | 新事件规则 |
| --- | ---: | ---: |
| 风扇状态 | 1 | 1 |
| 电源状态 | 1 | 1 |
| 温度 | 1 | 3 |
| 光模块在位及收发光功率 | 3 | 14 |
| 接口状态运行信息和统计信息 | 23 | 23 |
| M-LAG 状态 | 1 | 1 |
| 堆叠成员状态 | 1 | 1 |
| VRRP 状态 | 1 | 1 |
| CPU 使用率 | 1 | 3 |
| 内存使用率 | 1 | 3 |
| **合计** | **34** | **51** |

10 项健康／结构化变化检查项的规则全部绑定当前检查项版本，并通过现有工程复核和原子发布服务启用。
本次由同一 admin 身份执行用户授权的维护，调用服务已有的同人复核选项，覆盖原因写入审计，
没有伪造第二位审批人，也没有修改平台默认审批规则。

剩余 35 项的处理有明确区别：

- 32 项为证据模式，当前定义没有要求故障或变化事件，本次未擅自把资产、时钟、进程、
  ARP/MAC 明细等数据变成告警。后续需要这些事件时，应先在检查项定义中明确字段变化语义。
- 3 项为配置／日志文本比较，继续由文本比较 Profile 定义差异处理，不生成结构化数值策略。

## 旧规则处理

原有 32 条活动变化策略、52 条活动事件规则已停用；8 条策略草稿、23 条事件草稿退出审批候选。
120 条相关旧规则制作记录退出活动／待审批状态，避免旧候选再次发布。
当前活动规则集合准确等于本次生成的 34 条策略与 51 条事件规则，没有新旧规则混用。

历史规则内容、执行结果和报告保留用于审计，不再参与新巡检。原有规则缺失、错误字段引用、
已退役的光功率劣化条件不会通过旧运行包重新进入本次执行路径。

## 运行接入

为思科 70 条、华三 103 条检查项／命令适配器路径完成重新装配并启用，共 173 条。
平台原有 3 个文本运行包保留；全部 176 个活动运行包都引用活动检查项版本，

接入核查同时修正此前思科批次的两个问题：

  原错误版本未被巡检执行或运行包引用，已删除。
- 为 50 个 Parser 补齐已验证型号和样本摘要的兼容性记录；模板字节及输出字段合同不变。

思科样本任务 58 个命令单元、华三任务 96 个命令单元均为完成状态，无阻塞，未创建 Parser 自动生成任务。
运行包启用不会自动发起设备采集；实际巡检仍按选择的设备和检查项执行。
VRRP 等没有本次有效采集样本的检查项虽然规则已发布，也不能据此声称获得设备实测覆盖。

## 验证与数据边界

- 34 条策略的相同值抑制，以及 51 条规则的触发、非触发、字段隔离、恢复、阈值缺失等
  共 306 项执行器断言通过。这些是构造的边界案例，不冒充设备历史时间序列回放。
- 51 项相关自动化测试通过，包含旧字段引用和不支持条件类型的拒绝测试。
- 两批 201 条原始快照完整性与脱敏复验通过：182 条结构化样本、19 条配置原文处理结果不变。
- 对所有活动规则及运行包依赖进行了数据库核对，无旧规则活动残留，无过期检查项版本引用。

CPU、内存、温度和光功率规则遵循检查项声明的设备阈值；没有阈值时不使用隐藏的固定阈值。
缺少槽位、协议状态、通道或 DOM 数据时保持不完整，不能把“没有触发事件”解释为设备健康。
未根据本次静态样本声称完成真实设备故障、跨周期变化或告警恢复实测。

## 后续维护

`scripts/check_items/refresh_semantic_rules.py` 提供只读计划和显式执行两个入口：

```powershell
venv/Scripts/python.exe scripts/check_items/refresh_semantic_rules.py plan --plan .runtime/rule-refresh/plan.json
venv/Scripts/python.exe scripts/check_items/refresh_semantic_rules.py apply --plan .runtime/rule-refresh/plan.json --actor admin
```

`apply` 会停用计划范围内的旧规则及依赖运行包，再发布新规则；它不自动恢复运行包。
执行后应通过现有运行包装配服务核对和启用相应路径。检查项版本或语义变化会使计划失效，
需重新规划。执行状态保存在计划旁的 `.state.json`，可继续未完成的发布。

本次计划、逐规则验证、发布 ID、运行包装配记录和最终核对结果位于
`.runtime/check-item-rule-refresh/`。这些本地执行记录不作为公共 API。
