# 用户、App 使用权与数据范围

核对日期：2026-09-22。

## 授权方式

管理员在 `/users` 的应用使用权限中按用户或用户组授予 App。用户可用 App 列表由安装/启用状态、部署摘要及授权共同决定；管理员可访问已启用且就绪的 App，也不能绕过停用状态。

新业务 App 以“能否使用该应用”为权限边界，不另加应用内部角色层级。持有 rule-governance 使用权可进入设备与规则配置，inspection 控制巡检，materials 控制资料管理，assistant 控制问答。模型调用业务工具时还需对应源 App 使用权。

前端入口只负责展示。BFF 校验 JWT 和实时授权，Gateway 核对身份，Worker/Agent 工具继续执行准入检查。权限变化、停用、摘要不一致和源对象归属都可能导致请求拒绝；不能靠修改客户端字段获得权限。

实现见 [App 授权](../web/django_backend/bff/app_access.py)、[App 平台](../web/django_backend/bff/views/app_platform.py)和[页面能力判断](../web/react_frontend/src/apps/permissions.ts)。旧角色、netops.configure 和兼容 API 代码仍可存在，不再作为新业务 App 的统一使用权限说明。

## 数据范围与业务条件

会话、桌面设置、个人文件、公文等已有归属边界继续校验。App 使用权不等于可以读取其他人的个人数据，也不等于已经完成组织/租户级隔离。网盘团队角色沿用存储域的现有策略，见[网盘指南](storage-guide.md)。

规则发布、证据资格、任务生命周期、并发版本和数据完整性属于业务条件；有 App 使用权不代表可以跳过这些条件。新增权限设计不得重复建立应用内部角色体系。

## 验证

至少覆盖直接与用户组授予/撤销、无授权拒绝、停用后的拒绝、Worker 起跑复查、跨用户对象 ID、历史引用回查及伪造身份拒绝。个人桌面和壁纸按认证用户保存；登出/切换账号清空前端会话缓存，迟到的列表响应不得回写其他用户页面。
