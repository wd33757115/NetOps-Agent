# 用户角色、能力与数据范围

核对日期：2026-09-06。当前实现为角色与能力控制，数据隔离由各业务服务执行；它不是全平台统一租户隔离。

## 配置入口

管理员在 `/users` 管理账号。基础角色来自 Django Group，用户与分组默认保存在 PostgreSQL 的 `django` schema。

| 身份 | 当前用途 |
| --- | --- |
| admin | 用户管理、设备与规则配置，启动或授权规则自动发布 |
| operator | 执行允许的业务操作；默认不具有设备管理和规则制作能力 |
| operator + `netops.configure` | 可配置设备、制作规则及人工接管；自动发布仍需管理员授权 |
| viewer | 按页面和 API 提供的只读范围访问，不能执行运维 Skill 或修改网盘 |

在用户管理中设置网络配置授权，服务端保存到 `netops-config` 分组并返回 `netops.configure` 能力。管理 API 的字段为布尔值 `netops_configure`；不接受给 viewer 增加该授权。角色优先级为 admin、operator、viewer，超级用户按 admin 处理。

准确策略见 [roles.py](../web/django_backend/bff/roles.py)、[user_admin.py](../web/django_backend/bff/user_admin.py)与[共享网络权限策略](../src/auth/netops_access.py)。不要直接编辑 JWT 试图获得能力。

## 请求如何授权

React 的应用注册表与页面守卫控制可见入口。BFF 校验 JWT，读取用户角色与能力后转发；FastAPI 再执行对应业务权限检查。网络配置限制同时作用于两层 API，直接输入路由不能绕过授权。

BFF 内部头标识依赖内部网络边界；生产 FastAPI 不对外发布端口。头字段不是独立加密凭证，不能向不可信客户端开放可伪造内部头的网关入口。当前 Bearer 直连仅用于受控本地调试，不能替代 BFF 的实时能力上下文。

401 主要检查 token、过期与吊销；403 检查角色、能力、对象归属或 BFF 来源。登出/刷新轮换与会话吊销实现见 [auth.py](../web/django_backend/bff/auth.py)和[token_store.py](../src/auth/token_store.py)。权限变更后页面可能需要刷新用户信息，界面缓存不作为服务端授权依据。

## 与网络隔离的关系

角色/能力控制回答“可以执行什么操作”，类似按身份应用访问策略；数据范围回答“可以操作哪些对象”，更接近对不同实例分别限制路由可见范围。隐藏菜单只是展示层行为。

当前会话、公文和个人布局有用户归属约束；网盘按个人或团队目录范围授权，管理员按业务策略具有额外权限。网络设备和巡检不能据此推断已具备统一的组织/租户隔离。若新增组织隔离，需要定义 tenant/组织归属、强制查询范围、后台任务上下文、下载与审计约束，不能只增加一个角色或菜单条件。

规则自动发布授权还固定检查项版本、命令与设备范围，并有有效期。它与账号的长期配置能力不同，见 [自动制作指南](patrol-rule-autopilot-guide-2026-09-05.md)。

## 验证与账号维护

验证至少覆盖：普通 operator 的巡检入口、配置请求被拒绝、授权 operator 能制作但不能自行授权发布、viewer 写操作被拒绝，以及更换对象 ID 后的归属检查。

演示账号初始化命令会重设同名账号密码与分组，只用于明确的演示环境。已有正式账号不应重复运行；管理员创建与生产启动见 [部署说明](10_部署安装手册.md)。
